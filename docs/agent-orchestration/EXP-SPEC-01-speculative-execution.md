**Идентификатор:** EXP-SPEC-01.

**Место в развитии:** этап D [автоматического цикла задач](AUTOMATIC-TASK-CYCLE.md#d-эксперимент-спекулятивное-выполнение-задач).
Возврат к эксперименту обязателен по критериям завершения этапа C.
**Связанные документы:** [ROADMAP](ROADMAP.md), [AUTOMATIC-TASK-CYCLE](AUTOMATIC-TASK-CYCLE.md),
[рабочие пространства](implementation/workspaces-spec.md).

Сейчас это только план. Эксперимент, модельные прогоны и новая инфраструктура не запускаются.

## 1. Что это и чем это не является

**Спекулятивное выполнение** — выполнение вероятного следующего шага до того, как окончательно подтверждена его
зависимость.

Это **не** спекулятивное декодирование. Спекулятивное декодирование управляет генерацией токенов внутри модели. Здесь
речь о задачах, рабочих копиях и проверках приложения.

Различаются два случая:

| | Независимые задачи (этап C) | Спекулятивная задача (этап D) |
|---|---|---|
| Зависимость | нет | есть: задача B зависит от результата A |
| Основание для старта | задачи не пересекаются | явно записанное предположение о результате A |
| Результат | обычный, проходит проверку объединения | предварительный, пока предположение не подтверждено |

## 2. Гипотеза

Пока проверяющий оценивает результат задачи A, исполнитель готовит задачу B в отдельной рабочей копии. B исходит из
конкретного предполагаемого результата A.

- Если предположение подтверждается, заготовка используется.
- Если нет, заготовка пересматривается или отклоняется.

Ожидаемая польза — меньше времени до проверенного объединённого результата. Польза не обещается заранее: её нужно
измерить (§6).

## 3. Модель данных спекулятивного выполнения

Для каждого спекулятивного выполнения должны быть известны:

- задача и её зависимости;
- версии, на которых построено предположение:
  - версия плана;
  - версия исходного кода (commit базы);
  - версия предполагаемого контракта зависимости (например, API задачи A);
- условие подтверждения и условие отмены предположения;
- отдельный бюджет: время, ходы и токены. Он входит в общий бюджет, а не добавляется к нему;
- рабочая копия (отдельный worktree);
- состояние результата:
  - **предварительный** — предположение ещё не проверено;
  - **подтверждённый** — зависимость принята в том виде, который предполагался;
  - **устаревший** — зависимость изменилась, нужна повторная проверка или пересмотр;
  - **отклонённый** — предположение неверно или задача отменена.

Правила:

- Любое изменение зависимости переводит результат в «устаревший». Он требует повторной проверки.
- Предварительный результат не считается выполненной задачей. Он не объединяется автоматически.
- Подтверждённый результат проходит те же обязательные проверки и ревью, что и обычный (принцип 4 цикла).
- Состояние выводится из журнала запусков (принцип 8 цикла). Отдельного статуса, который может разойтись с
  журналом, нет.

## 4. Безопасность

- Worktree изолирует файлы, но не внешние эффекты.
- Спекулятивная работа не выполняет:
  - push;
  - деплой;
  - изменения общих баз данных;
  - отправку сообщений;
  - другие необратимые действия.
- Действия после успеха (commit в общую ветку, push, QA) выполняются только для подтверждённого результата, так же как
  сейчас в `finish.ts`.
- Права агента не расширяются. Если для запрета внешних эффектов нужны более узкие права, это отдельное явное решение
  пользователя, а не молчаливое сужение.
- Отмена прекращает связанную работу и сохраняет диагностику: журнал, вывод, diff рабочей копии.
- После перезапуска приложения отменённая ветка не оживает.

## 5. Что видит пользователь

Интерфейс объясняет состояние простыми словами:

- «Готовится заранее — ждёт принятия API»;
- «Предположение подтверждено»;
- «Требуется пересмотр после изменения API».

Кроме того, видно:

- на каком предположении построена заготовка;
- сколько бюджета она израсходовала;
- что будет при отмене.

## 6. Как оценивать пользу

**С чем сравнивать.** С обычным исполнением, которое уже использует разрешённый параллелизм этапа C. Сравнение только с
искусственно последовательным вариантом не годится.

**Условия сравнения:**

- одинаковые исходные проекты, требования, проверки и версии инструментов;
- зафиксированные модели и права, сопоставимые ограничения ресурсов;
- несколько сопоставимых прогонов в порядке, который не даёт преимущества прогретым кэшам (например, чередование);
- критерии принятия эксперимента определены до прогонов.

**Что измерять:**

- время до проверенного и объединённого результата;
- успешность выполнения и найденные дефекты;
- число вмешательств пользователя;
- токены и известную стоимость;
- объём отброшенной работы;
- конфликты, переделки и повторные проверки;
- соблюдение общего бюджета.

**Правила оценки:**

- Неизвестная стоимость не приравнивается к нулю. Она записывается как «неизвестно».
- Ускорение не обещается заранее.
- Один удачный запуск не доказывает пользу.

## 7. Обязательные сценарии

1. Предположение подтвердилось.
2. Проверяющий изменил контракт зависимости.
3. Пользователь отменил задачу.
4. Исчерпан бюджет.
5. Приложение перезапущено.
6. Обнаружен конфликт при объединении.

Для каждого сценария проверяется:

- итоговое состояние результата;
- отсутствие внешних эффектов;
- сохранность диагностики;
- что предварительный результат не оказался объединён.

## 8. Результат пилота

Решение **«внедрять / доработать / отказаться»** с доказательствами по §6 и §7. Отрицательный результат — тоже
завершённый эксперимент.

## 9. Готовность к пилоту (проверяется после этапа C)

- Этапы A, B и C приняты внешним ревью.
- Есть задачи с явными зависимостями (этап B) и параллельные worktree с проверкой объединения (этап C).
- Есть способ записать предположение и версии, на которых оно построено.
- Определены критерии принятия эксперимента и набор сопоставимых задач.
- Готов план ограниченного пилота: объём, бюджет, число прогонов, сценарии §7.

### 11.1. Предлагаемые критерии принятия

Определяются до прогонов (§6). Пилот «внедрять», только если выполнено всё:
- время до проверенного и объединённого результата пары «A → B» в среднем меньше **не менее чем на 20 %**, чем у
  обычного исполнения C (B ждёт «Готово» A и вливания в итог доски);
- успешность («Готово — подтверждено проверками» у обеих задач) не ниже, чем у обычного;
- ни одного внешнего эффекта и ни одного объединённого предварительного результата (§4, §7);
- число вмешательств человека не больше, чем у обычного;
- известная стоимость (вызовы, токены) не больше чем в 1,5 раза; неизвестная записывается как «неизвестно».

«Доработать» — если польза есть, но не выполнен один из пунктов, кроме безопасности. «Отказаться» — нарушение
безопасности или нет пользы.

### 11.2. Набор задач

Фикстурный проект (Node, `node --test`), 3 пары «A → B»: B использует API, который вводит A:
1. A добавляет функцию разбора конфигурации, B — команду, которая её вызывает;
2. A меняет формат ответа модуля, B — его потребителя;
3. A добавляет поле в модель данных, B — его показ.

В паре 2 предположение заведомо может не подтвердиться (проверяющий A просит другой формат): сценарий §7.2.

### 11.3. План пилота

- **Сначала без моделей:** сценарии §7 (подтвердилось; контракт изменён; отмена; бюджет; перезапуск; конфликт) — на
  подставных CLI, как smoke этапов B–C. Проверяется состояние результата, отсутствие внешних эффектов, сохранность
  диагностики, что предварительный результат не объединён.
- **Потом с моделями** (с разрешения владельца): 3 пары × 2 варианта (обычный C и спекулятивный) × 2 прогона, порядок
  вариантов чередуется. Оценка — до 8 вызовов на задачу, около **200 вызовов** всего; бюджет каждой пары общий для
  обоих её запусков (§3). Те же версии CLI, модели и права во всех прогонах; хеши `config.toml` и настроек Claude до
  и после.
- **Итог** — решение §8 с таблицей метрик §6 по каждой паре.
