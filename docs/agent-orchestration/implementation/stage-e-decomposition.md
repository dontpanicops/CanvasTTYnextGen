# Этап E: агенты разбивают задачу на подзадачи

**Статус: ревизия 2, после первого круга ревью (скептик, критик), 2026-10-19.** Решения владельца — §11. Реализация —
после C4 ([этап C](stage-c-parallel.md) §9) и повторного ревью этой ревизии.

Новый этап, его нет в порядке A → B → C → D [автоматического цикла](../AUTOMATIC-TASK-CYCLE.md). Владелец попросил
«полную автоматизацию — завёл задачу, агенты сами заводят подзадачи и берут их в работу» (2026-10-19). Опирается на
доску ([этап B](stage-b-board.md)), параллельность и итог доски ([этап C](stage-c-parallel.md)), отдельный запуск с
конвертом v3 ([C3](stage-c3-conflicts.md) §2, §7.2, §13).

Ревизия 1 описывала разбиение как «один ход лида без нового состояния». Ревью показало, что это неверно:
- журнал знает только назначения `plan / execute / review / final_review` и завершение `confirmed / no_checks` после
  финального ревью (`journal.ts:395, 569, 1258`); без плана цикл всегда идёт в `replan()` (`cycle.ts:203`);
- автопилот видит только запуски с `goal.task` (`manager.ts:841`) и ждёт неизвестный запуск вечно (`taskBoard.ts:457`);
- приписки к тексту упираются в 8000 знаков (`orchestrationService.ts:475`).

Ревизия 2 называет все нужные изменения (§3, §5, §6) и убирает хранимый статус из `board.json` (§2).

## 0. Что есть и чего нет

Есть:
- задача доски: текст, требования (1–32 × 500), зависимости без циклов;
- автопилот доски: задачи по порядку и зависимостям, до 4 сразу (только «Отдельная копия» и worktree), бюджет запусков
  и минут;
- зависимая задача стартует от итога доски, где влиты её зависимости (C2);
- внутри запуска лид разбивает задачу на этапы; покрытие требований условиями проверяет приложение (принцип 9);
- отдельный запуск не на связи, с конвертом v3 и своим `kind` (C3).

Нет:
- задачу нельзя превратить в несколько задач доски: всё большое идёт одним запуском;
- агент не может добавить задачу на доску; пожелания проверяющего (`severity: "wish"`) остаются в итоге запуска.

## 1. Сценарии

1. **Разбить.** Человек заводит T-1 с отметкой «Разбить на подзадачи». Автопилот (или кнопка «Разбить» на карточке)
   начинает **запуск разбиения** (§3): лид читает проект и предлагает подзадачи. Приложение проверяет предложение (§4) и
   одной записью заводит T-2…T-5 (§5). T-1 ждёт их. Автопилот берёт подзадачи по зависимостям. Когда все они «Готово» и
   в итоге доски, T-1 идёт **завершающим запуском** (§6): проверяет требования T-1 как они записаны и доделывает
   недостающее.
2. **Лид считает, что делить не нужно** (`whole`). T-1 выполняется целиком, как обычная задача; на карточке — «не
   разбита: <почему лида>».
3. **Предложение не прошло проверку.** Лид получает причины и один повтор. Второй отказ — T-1 «на проверке: разбиение не
   удалось» с выбором «Разбить ещё раз», «Выполнить целиком», «Изменить задачу».
4. **Вопрос лида.** Пауза ожидания ответа, как у плана; ответ — с карточки T-1 через панель запуска разбиения.
5. **Пожелание проверяющего → задача** (§8). Кнопка «Сделать задачей» в итоге запуска.
6. **Откат на старую сборку** (§9): подзадачи видны как обычные задачи, T-1 — как задача, которая от них зависит.

## 2. Модель данных

`board.json` остаётся версии 1. Хранится только то, что задал человек или приложение при создании; статус разбиения
выводится из журнала запуска разбиения и из подзадач (принцип 8).

```ts
interface BoardTask {
  // ...как сейчас
  decompose?: true;                                   // человек отметил «Разбить на подзадачи»
  parentId?: string;                                  // подзадача: её родитель (той же папки и пространства)
  covers?: string[];                                  // подзадача: требования родителя, "R1".."R32"
  origin?: { kind: "decomposition"; runId: string }   // кем создана: запуском разбиения
         | { kind: "finding"; runId: string; findingId: string }; // или из пожелания (§8)
}
```

Старые сборки эти поля не проверяют и сохраняют: задача читается целиком, `isTask` лишних ключей не отвергает,
`update` и `archive` делают `{ ...t, ... }` (`boardStore.ts:30–41, 88, 174, 184`). Проверить на упакованных сборках (E0).

Правила:
- **Глубина одна:** у задачи с `parentId` нет `decompose`; форма и хранилище его не принимают.
- **Подзадач** в одном разбиении 2…10.
- После создания у родителя `dependsOn` = его прежние зависимости + все подзадачи. Ожидание родителя идёт правилами доски
  и C2.
- «Выполнить целиком» — человек снимает отметку `decompose`. Ответ лида `whole` отметку не снимает: статус берётся из
  журнала (§2.1).
- «Требования менялись после разбиения» — сравнение текущих требований T-1 с требованиями цели последнего запуска
  разбиения (копия в `board.json` не хранится).

### 2.1. Что выводится для родителя

Родитель — задача с `decompose: true`, у которой нет неархивных подзадач и нет своего запуска. Его состояние — из
последнего запуска разбиения этой задачи (новый признак фактов `kind: "decomposition"`, §7).

| Запуск разбиения | Колонка | Причина (новая — **жирным**) | Действия человека |
|---|---|---|---|
| нет | очередь | — | «Разбить» |
| идёт | работа | **`decomposing`** «разбивается на подзадачи» | «Открыть разбиение», «Остановить» |
| пауза, вопрос лида | работа | `waits_answer` (как у запусков) | «Ответить» |
| пауза по лимиту провайдера (C4) | работа | как у запусков в C4 | как в C4 |
| `completed`, `proposed`, подзадачи ещё не созданы | работа | **`decomposing`** | — (main создаёт их, §5) |
| `completed`, `whole` | очередь | — (строка «не разбита: …») | «Запустить» как обычную задачу |
| `completed`, `rejected`; `failed`; `stopped` | проверка | **`decomposition_failed`** + деталь `rejected` / `failed` / `stopped` / `parent_started` | «Разбить ещё раз», «Выполнить целиком», «Изменить» |

Родитель с подзадачами — обычная задача, ждущая зависимостей (`waits_task`, `waits_merge`). Дополнительно на его
карточке:
- строка «подзадачи: 3 из 5 в итоге доски»;
- ссылки на подзадачи;
- пометки «подзадача T-3 в архиве» и «требования менялись после разбиения».

### 2.2. Подзадачи в особых случаях

- **Подзадача в архиве** не держит родителя: в его ожидании архивные зависимости с `parentId` = родитель не считаются.
  Для обычных зависимостей правило этапа B не меняется. Требования, которые она закрывала, всё равно проверит
  завершающий запуск (§6).
- **Подзадача удалена** (без запусков): хранилище уже убирает её из `dependsOn` (`boardStore.ts:198`), дальше — как с
  архивом.
- **Подзадача на паузе, упала, остановлена, ждёт человека:** родитель ждёт с той же причиной, что любая зависимая задача
  (`waits_task` с ключом). Автопилот ведёт себя по правилам этапа B §5.2.
- **«Пропустить» при объединении подзадачи** (C1): она «Готово», но не в итоге доски. Родитель стоит
  `waits_merge` с её ключом. Действие человека — объединить её или отправить в архив. Сам родитель не стартует.
- **Родитель в архиве:** автопилот не берёт его подзадачи; сами подзадачи в архив не уходят. На их карточках — «родитель
  в архиве».
- **«Разбить ещё раз»** доступно, только если у родителя нет своего запуска и все его подзадачи в архиве или их нет.
  Иначе — отказ `has_subtasks`.
- **У родителя уже был свой запуск** (например, после отката старая сборка выполнила его целиком): подзадачи не
  создаются, разбиение получает деталь `parent_started`.

## 3. Запуск разбиения

Отдельный запуск, как запуск разрешения C3:
- журнал с конвертом v3, `minReaderVersion` 3, `run.created { goal, kind: "decomposition" }`, правила v2;
- не на связи: в списке запусков его нет, открывается с карточки задачи.

### 3.1. Цель

`checkDecomposition`, по образцу `checkResolution` (`orchestrationService.ts:501`):
- `decomposition: { taskId, key }` — id и `T-n` родителя;
- текст и требования родителя;
- `workMode: "copy"` всегда — запуск не занимает папку проекта (`folder_busy`). Копия от итога доски, если он есть, иначе
  от HEAD;
- без `prepare`, `finish`, `task`, `base`, `reviewPlan`;
- `commands` пустые разрешены только этому виду запуска: правило «права требуют команд» (`orchestrationService.ts:464`)
  для него снято;
- `access` и модель лида — из профиля проекта;
- лимиты: `turns` 3, `runMs` и `leadTurnMs` 10 минут.

### 3.2. Изменения журнала и цикла

| Место | Изменение |
|---|---|
| `TURN_PURPOSES`, схема `orch.turn` (`journal.ts:395, 592`) | назначение `decompose`, только в журнале `kind: "decomposition"` |
| `run.created` (`journal.ts:621`), признак журнала (`isResolutionJournal` и соседи, `journal.ts:1532, 1570, 1606`) | `kind` — `"resolution" \| "decomposition"`; общий признак «журнал отдельного запуска» |
| новые записи | `decomposition.proposed { turnId, proposal: TextRef }` — предложение прошло проверку §4; `decomposition.rejected { turnId, reasons: TextRef }` — не прошло |
| `run.status` (`journal.ts:569`) | `completion.kind` `"proposed" \| "whole" \| "rejected"`, только в журнале разбиения; `completedAllowed` (`journal.ts:1258`) для него — последний ход `decompose` и запись `proposed` или `rejected` либо ответ `whole` |
| `decide()` (`cycle.ts:203`) | ветка разбиения: нет хода → ход `decompose`; последний `rejected`, отказов 1 → ход `decompose` с причинами; отказов 2 → `completed rejected`; `proposed` или `whole` → `completed`; вопрос → пауза `awaiting_answer`, ответ → ход `decompose` с ответом |
| `completion()` (`cycle.ts:325`) | то же для этого вида |
| песочница лида | как у хода `plan` |

### 3.3. Ответ лида

JSON-схема хода `decompose`:

```json
{ "tasks": [ { "id": "S1", "title": "…", "text": "…", "criteria": ["…"], "dependsOn": [], "covers": ["R1", "R2"] },
             { "id": "S2", "title": "…", "text": "…", "criteria": ["…"], "dependsOn": ["S1"], "covers": ["R3"] } ],
  "whole": null, "question": null }
```

- `id` — `S1…S10`, уникальные;
- `title` — 1…200 знаков, уникальные в списке;
- `text` — 1…6000 знаков (остальное место — за приложением, §6);
- `criteria` — 1…16 × 1…500 знаков;
- `dependsOn` — `id` этого списка;
- `covers` — `R<n>` родителя;
- `whole` — 1…2000 знаков или `null`; `question` — как у плана. Ровно одно из трёх: непустой `tasks`, `whole`,
  `question`.

## 4. Проверка предложения (приложение)

Предложение принимается, только если:
- подзадач 2…10, поля в пределах §3.3;
- `dependsOn` ссылаются на `id` этого списка, без циклов;
- **каждое требование родителя `R1…Rn` покрыто** хотя бы одной подзадачей, и других `R` нет (принцип 9);
- у родителя нет своего запуска, и все его прежние подзадачи в архиве.

Проверка формальная. По смыслу требования родителя проверяет завершающий запуск (§6), поэтому он обязателен.

Отказ — запись `decomposition.rejected` с причинами. Лид получает причины в следующем ходе; после второго отказа —
`completed rejected`.

## 5. Создание подзадач

Делает main, а не ход агента, после `completed proposed`:
- **одна запись `board.json`** (`change()`): все подзадачи с `parentId`, `covers`, `origin: { kind: "decomposition",
  runId }`, их `dependsOn` по `S`, новый `dependsOn` родителя;
- `order` подзадач — между родителем и следующей задачей очереди, в порядке предложения;
- **без повторов**: если на доске есть задача с этим `origin.runId`, ничего не создаётся;
- **восстановление**: при чтении доски и на шаге автопилота main ищет запуски `proposed`, по которым задачи не созданы, и
  создаёт их. Так сбой между завершением запуска и записью доски ничего не теряет и не задваивает;
- каждая подзадача получает следующий `T-n` пространства.

## 6. Цель подзадачи и завершающего запуска

Приписки не входят в текст задачи: новое необязательное поле цели (только v2), его проверяет `checkGoal`; запрос
исполнителя и проверяющего показывает его отдельным блоком.

- **Подзадача:** `part: { of: "T-1", title, requirements: [{ id: "R2", text }] }` — требования родителя, которые она
  закрывает, дословно (до 32 × 500). Это контекст, а не её требования: принимается подзадача по своим `criteria`.
- **Завершающий запуск родителя:** `parts: { keys: ["T-2", …] }`. В запросе: «Подзадачи T-2…T-5 выполнены и влиты в итог
  доски. Проверьте требования этой задачи на текущем коде и доделайте только недостающее». Лид планирует сам,
  проверяющий проверяет требования T-1 дословно (принцип 4).
- Оба поля добавляет `goalFor` (`taskBoard.ts:410`) и ручной старт задачи с карточки (тот же сбор цели), из данных доски.

### 6.1. По режимам работы

| Режим | Подзадачи | Родитель |
|---|---|---|
| «Отдельная копия» или worktree, автопилот | параллельно, до N сразу, от итога доски (C1, C2) | от итога доски, где влиты все неархивные подзадачи |
| «Отдельная копия» без автопилота | человек запускает и объединяет каждую («Объединить», C1) | стоит `waits_merge`, пока подзадачи не в итоге доски |
| «Папка проекта» | по одной (`autopilotStep`, `boardAutopilot.ts:100`), в папке проекта | после последней подзадачи, в папке проекта |

Конфликт объединения между параллельными подзадачами — обычный конфликт объединения: его разрешает человек или агент по
настройке «Конфликты» (C3).

## 7. Автопилот

- **Факты:** в `RunTaskFacts` новое поле `kind: "task" | "decomposition"`. Факты разбиения входят в вид доски, но не в
  запуски задачи: `boardStatuses` ищет их отдельно, по `decomposition.taskId`.
- **Свой список**, как `agents` у C3 (`boardAutopilot.ts:44`): идущие запуски разбиения автопилота.
  - Каждый занимает место и считается одним запуском бюджета.
  - `wait` по ним не нужен: запуск виден в фактах с `kind: "decomposition"`.
- **Шаг `decompose`:** первая по порядку задача с `decompose: true`, без подзадач, без своего запуска и без разбиения.
  Последнее разбиение такой задачи должно отсутствовать или быть `rejected`/`failed`/`stopped`, а человек должен нажать
  «Разбить ещё раз».
- **`next` и `nextTask`** (`taskBoard.ts:593`) не берут родителя с `decompose: true`, пока у него нет подзадач и
  последнее разбиение не `whole`.
- **После `proposed`** подзадачи создаются (§5), автопилот берёт их следующим шагом (решение владельца 2).
- **Остановки:**
  - `decomposition_failed` у родителя — ожидание человека, как `last_failed` (этап B §5.2); автопилот берёт другие задачи;
  - вопрос лида — как `waits_answer`.
- **Бюджет общий** для разбиения, подзадач и завершающего запуска. Если он кончился посреди цепочки — обычная остановка
  «бюджет». Подзадачи и родитель остаются как есть; следующее «Запустить доску» продолжит.

## 8. Пожелания проверяющего → задачи

В итоге запуска у **открытого** пожелания — кнопка «Сделать задачей» (решение владельца 4). Создаётся задача той же
папки:

| Поле | Откуда |
|---|---|
| `title` | `problem`: первые 200 знаков, обрезка по слову с «…» |
| `text` | `problem`, `evidence`, `closeWhen` и строка «Из пожелания F3 запуска T-2»; до 8000, обрезка с «…» |
| `criteria` | `[closeWhen]`, обрезка до 500 с «…» |
| `origin` | `{ kind: "finding", runId, findingId }` |

- Дубликат по паре `(runId, findingId)` не создаётся: кнопка становится «Задача T-7».
- Закрытое пожелание кнопки не имеет.
- Автоматически пожелания в задачи не попадают.

## 9. Совместимость и откат

- **`board.json`** v1 с новыми полями. Старые сборки (1.5.16 … последняя до E) видят подзадачи и родителя как обычные
  задачи с зависимостями.
  - Родитель с `decompose` без подзадач старая сборка выполнит целиком.
  - После возврата на новую сборку разбиение такого родителя не создаёт подзадачи (`parent_started`, §2.2).
- **Журнал разбиения** — конверт v3 по образцу C3: старые сборки показывают его только для просмотра.
- **Поля цели `part` и `parts`**: проверить, что старые сборки открывают запуск с ними хотя бы для просмотра (E0). Если
  нет — запуски подзадач идут с конвертом v3 по правилам C3, а решение записывается здесь до кода.

## 10. Интерфейс

- **Форма задачи:** галочка «Разбить на подзадачи». Её нет у подзадачи, и она недоступна, если у задачи есть свой
  запуск или неархивные подзадачи.
- **Карточка родителя:** причины и действия по §2.1.
  - «Открыть разбиение» открывает панель запуска разбиения. Предложение видно там на вкладке «План»: список подзадач с
    зависимостями и покрытием `R`. Причины отказа — в ленте.
  - После создания на карточке строка «подзадачи: k из n в итоге доски», ключи подзадач (по нажатию — к карточке) и
    пометки §2.1.
- **Карточка подзадачи:** «часть T-1» (по нажатию — к родителю); в подробностях — «закрывает R2, R3 задачи T-1»;
  пометка «родитель в архиве».
- **Итог запуска:** «Сделать задачей» / «Задача T-7» у пожеланий.

## 11. Решения владельца (2026-10-19)

1. **Порядок:** E — после C4.
2. **Подзадачи в автопилоте:** создаются сами после проверки приложения (§4); настройки «показывать мне» в первой
   версии нет.
3. **Кто решает разбивать:** только задачи, отмеченные человеком «Разбить на подзадачи». Лид может ответить `whole`.
4. **Пожелания проверяющего:** кнопка «Сделать задачей» для человека; автоматически в очередь не попадают (§8).

Решения по умолчанию, без отдельного вопроса:
- глубина одна;
- до 10 подзадач;
- завершающий запуск обязателен (§4);
- подзадачи идут по профилю проекта, как любая задача: те же права, модели, команды.
