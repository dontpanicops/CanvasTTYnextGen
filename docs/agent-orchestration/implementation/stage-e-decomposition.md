# Этап E: агенты разбивают задачу на подзадачи

**Статус: ревизия 3, после второго круга ревью (скептик, критик), 2026-10-19.** Решения владельца — §11. C4 влит и
вышел в 1.5.20 ([этап C](stage-c-parallel.md) §9). Реализация — по плану §12; E0 (откат до кода) пройден — §9.

Новый этап, его нет в порядке A → B → C → D [автоматического цикла](../AUTOMATIC-TASK-CYCLE.md). Владелец попросил
«полную автоматизацию — завёл задачу, агенты сами заводят подзадачи и берут их в работу» (2026-10-19). Опирается на:
- доску ([этап B](stage-b-board.md));
- параллельность и итог доски ([этап C](stage-c-parallel.md));
- отдельный запуск, созданный приложением, с конвертом v3 — запуск разрешения [C3](stage-c3-conflicts.md) §2, §13;
- поведение автопилота на лимите провайдера ([C4](stage-c4-limits.md) §2, §3, §10).

Ревизия 1 описывала разбиение как «один ход лида без нового состояния». Ревью показало, что это неверно:
- журнал знает только назначения `plan / execute / review / final_review` и завершение `confirmed / no_checks` после
  финального ревью (`journal.ts`: `TURN_PURPOSES`, `run.status`, `completedAllowed`);
- без плана цикл всегда идёт в `replan()` (`cycle.ts`: `decide`);
- автопилот видит только запуски с `goal.task` (`manager.ts`: `metaOf`, `board()`).

Ревизия 2 назвала нужные изменения журнала и убрала хранимый статус из `board.json`.

Ревизия 3 исправляет находки второго круга:
- запуск разбиения встроен в учёт автопилота после C3/C4 (§7): места, бюджет, лимит провайдера, последовательный шаг;
- описаны старт, слежение и восстановление (§3.4), отказы создания подзадач (§5.1);
- повтор создания проверяется по отметке на родителе, а не по наличию подзадач (§2, §5);
- подзадачи наследуют зависимости родителя (§2);
- без новых полей цели: приписки — в тексте задачи (§6), риск совместимости запусков задач снят;
- пожелания проверяющего → задачи вынесены в отдельный шаг после E (§8).

Ссылки на код — по именам функций: номера строк меняются от этапа к этапу.

## 0. Что есть и чего нет

Есть:
- задача доски: текст (до 8000), требования (1–32 × 500), зависимости без циклов;
- автопилот доски:
  - задачи по порядку и зависимостям, до 4 сразу (только «Отдельная копия» и worktree);
  - бюджет запусков и минут; попытки разрешения конфликта (C3) — запуски бюджета, ожидание лимита (C4) минут не
    тратит;
  - на лимите провайдера ждёт и продолжает свои запуски (C4 §2);
  - свой запуск, остановленный, упавший или на паузе не по вопросу, выключает автопилот (`autopilotStep`,
    `autopilotParallelStep`: `run_stopped`, `run_failed`, `halt`);
- зависимая задача стартует от итога доски, где влиты её зависимости (C2);
- внутри запуска лид разбивает задачу на этапы; покрытие требований условиями проверяет приложение (принцип 9);
- запуск, созданный приложением, не на связи, с конвертом v3 и своим `kind`; manager следит за ним таймером и после
  перезапуска (C3: `startResolution`, `syncResolutions`).

Нет:
- задачу нельзя превратить в несколько задач доски: всё большое идёт одним запуском;
- агент не может добавить задачу на доску.

## 1. Сценарии

1. **Разбить.** Человек заводит T-1 с отметкой «Разбить на подзадачи». Автопилот (или кнопка «Разбить» на карточке)
   начинает **запуск разбиения** (§3): лид читает проект и предлагает подзадачи. Приложение проверяет предложение (§4) и
   одной записью заводит T-2…T-5 (§5). T-1 ждёт их. Автопилот берёт подзадачи по зависимостям. Когда все они «Готово» и
   в итоге доски, T-1 идёт **завершающим запуском** (§6): проверяет требования T-1 как они записаны и доделывает
   недостающее.
2. **Лид считает, что делить не нужно** (`whole`). T-1 выполняется целиком, как обычная задача; на карточке — «не
   разбита: <почему лида>».
3. **Предложение не прошло проверку.** Лид получает причины и один повтор. Второй отказ — T-1 «разбиение не удалось»
   с выбором «Разбить ещё раз», «Выполнить целиком», «Изменить задачу».
4. **Вопрос лида.** Пауза ожидания ответа, как у плана; ответ — с карточки T-1 через панель запуска разбиения.
5. **Лимит провайдера во время разбиения.** Как у запусков задач в C4: автопилот ждёт и продолжает после сброса.
6. **Откат на старую сборку** (§9): подзадачи видны как обычные задачи, T-1 — как задача, которая от них зависит.

## 2. Модель данных

`board.json` остаётся версии 1. Хранится только то, что задал человек или приложение при создании; статус разбиения
выводится из журнала запуска разбиения и из подзадач (принцип 8).

```ts
interface BoardTask {
  // ...как сейчас
  decompose?: true;       // человек отметил «Разбить на подзадачи»
  decomposedBy?: string;  // родитель: runId разбиения, по которому созданы его подзадачи (пишется той же записью)
  parentId?: string;      // подзадача: её родитель (той же папки и пространства)
  covers?: string[];      // подзадача: требования родителя, которые она закрывает, "R1".."R32"
}
```

Старые сборки эти поля, по коду, не проверяют и сохраняют: задача читается целиком, `isTask` лишних ключей не
отвергает, `update` и `archive` делают `{ ...t, ... }` (`boardStore.ts`). Это гипотеза, её проверяет E0 на упакованных
сборках; до её записи в §9 код E1 не начинается.

Правила:
- **Глубина одна:** у задачи с `parentId` нет `decompose`; форма и хранилище его не принимают.
- **Подзадач** в одном разбиении 2…10.
- **Зависимости:**
  - подзадача без зависимостей внутри предложения получает прежние зависимости родителя, остальные — свои из
    предложения;
  - у родителя `dependsOn` = его прежние зависимости + все подзадачи.

  Дальше ожидание идёт правилами доски и C2.
- **«Выполнить целиком»** — человек снимает `decompose` (и `decomposedBy`, если подзадач не осталось). Ответ лида
  `whole` отметку не снимает: статус берётся из журнала (§2.1).
- **«Требования менялись после разбиения»** — сравнение текущих требований T-1 с требованиями цели запуска
  `decomposedBy` (копия в `board.json` не хранится). Тексты уже созданных подзадач — снимок на момент разбиения, они не
  меняются.

### 2.1. Что выводится для родителя

Родитель — задача с `decompose: true`. Его состояние:
- без `decomposedBy` — из последнего запуска разбиения этой задачи (факты с `decompositionOf`, §7);
- с `decomposedBy` — из подзадач.

| Состояние | Колонка | Причина (новая — **жирным**) | Действия человека |
|---|---|---|---|
| разбиений нет | очередь | — | «Разбить» |
| разбиение идёт | работа | **`decomposing`** «разбивается на подзадачи» | «Открыть разбиение», «Остановить» |
| пауза, вопрос лида | работа | `waits_answer` (как у запусков) | «Ответить» |
| пауза по лимиту провайдера | работа | как у запусков в C4 («исчерпан лимит … до 15:00») | ждать или «Продолжить» в панели |
| пауза по другой причине (сбой отчёта, `environment_error` без лимита, `limit_reached`, `paused(recovered)`) | работа | **`decomposition_paused`** + причина паузы | «Открыть разбиение» (там «Продолжить»), «Остановить» |
| `completed proposed`, подзадачи не созданы | работа | **`decomposing`** | — (main создаёт их, §5) |
| `completed whole` | очередь | — (строка «не разбита: …») | «Запустить» как обычную задачу |
| `completed rejected`; `failed`; `stopped`; создать нельзя (§5.1) | проверка | **`decomposition_failed`** + деталь `rejected` / `failed` / `stopped` / код §5.1 | «Разбить ещё раз», «Выполнить целиком», «Изменить» |
| `decomposedBy` есть, неархивных подзадач нет | проверка | **`subtasks_gone`** «подзадачи удалены или в архиве» | «Разбить ещё раз», «Выполнить целиком» |

Родитель с неархивными подзадачами — обычная задача, ждущая зависимостей (`waits_task`, `waits_merge`). Дополнительно на
его карточке:
- строка «подзадачи: 3 из 5 в итоге доски»;
- ссылки на подзадачи;
- пометки «подзадача T-3 в архиве» и «требования менялись после разбиения».

Команды действий:

| Действие | Команда | Отказы |
|---|---|---|
| «Разбить», «Разбить ещё раз» | `board:decompose {taskId}` → `startDecomposition` (§3.4) | `task_active_run`, `decomposition_active`, `has_subtasks`, `deps_not_ready`, `damaged`, `newer_version` |
| «Выполнить целиком» | `board:update` с `decompose: false` | `decomposition_active`; есть неархивные подзадачи — `has_subtasks` |
| «Остановить» | stop запуска разбиения (как любой запуск) | как у stop |

### 2.2. Подзадачи в особых случаях

- **Подзадача в архиве** не держит родителя: архивные зависимости, у которых `parentId` равен этому родителю, не
  считаются. Это правка трёх мест, где сейчас архивная зависимость держит всегда: `depsOf` в `boardStatuses`, отбор
  `next` в `autopilotParallelStep` и `taskOk` в manager. Для обычных зависимостей правило этапа B не меняется.
  Требования, которые она закрывала, всё равно проверит завершающий запуск (§6).
- **Подзадача удалена** (без запусков): хранилище уже убирает её из `dependsOn` (`boardStore.ts`: `remove`), дальше — как с
  архивом. Повторного создания нет: родитель хранит `decomposedBy` (§5).
- **Подзадача на паузе, упала, остановлена, ждёт человека:** родитель ждёт с той же причиной, что любая зависимая задача
  (`waits_task` с ключом). Автопилот ведёт себя по правилам этапа B §5.2.
- **«Пропустить» при объединении подзадачи** (C1): она «Готово», но не в итоге доски. Родитель стоит `waits_merge` с её
  ключом. Действие человека — объединить её или отправить в архив. Сам родитель не стартует.
- **Родитель в архиве:** автопилот не берёт его подзадачи; сами подзадачи в архив не уходят. На их карточках — «родитель
  в архиве».
- **У родителя уже был свой запуск** (например, после отката старая сборка выполнила его целиком): подзадачи не
  создаются, разбиение получает деталь `parent_started` (§5.1).

## 3. Запуск разбиения

Отдельный запуск, как запуск разрешения C3:
- журнал с конвертом v3, `minReaderVersion` 3, `run.created { goal, kind: "decomposition" }`, правила v2;
- не на связи: в списке запусков его нет, открывается с карточки задачи.

### 3.1. Цель

`checkDecomposition`, по образцу `checkResolution` (`orchestrationService.ts`):
- `decomposition: { taskId, key, base }`:
  - `taskId` и `key` — id и `T-n` родителя;
  - `base` — коммит вершины итога доски, если итог есть, иначе HEAD папки проекта (как `resolution.base`; проверка — 40
    знаков hex, коммит есть в репозитории);
- текст и требования родителя — его цель, как у задачи;
- `workMode: "copy"` всегда — запуск не занимает папку проекта (`folder_busy`); копия от `decomposition.base`;
- без `prepare`, `finish`, `task`, `base`, `reviewPlan`;
- `commands: []`. Пустые команды в v2 уже проходят `checkGoal`, но означают «лид предлагает проверки» (`proposesChecks`,
  путь `checksProposal` в `decide`). Для `kind: "decomposition"` `proposesChecks` возвращает `false`, а ветка разбиения в
  `decide()` стоит раньше проверки предложенных команд;
- `access` и модель лида — из профиля проекта;
- лимиты:
  - `turns` 6 — ход, отказ и повтор, вопрос и ответ, плюс один сбойный ход;
  - `leadTurnMs` 10 минут;
  - `runMs` по умолчанию (`DEFAULT_LIMITS`). Он считается от создания запуска вместе с паузами (`nextAction`), поэтому
    короткий `runMs` оборвал бы запуск после долгого ответа человека или сброса лимита.

### 3.2. Изменения журнала и цикла

| Место | Изменение |
|---|---|
| `TURN_PURPOSES`, схема `orch.turn` (`journal.ts`) | назначение `decompose`, только в журнале `kind: "decomposition"` |
| `run.created`, признак журнала (`isResolutionJournal`, `isResolutionHead` и соседи, `journal.ts`) | `kind` — `"resolution" \| "decomposition"`; общий признак «журнал запуска приложения» |
| новые записи | `decomposition.proposed { turnId, proposal: TextRef }` — предложение прошло проверку §4; `decomposition.rejected { turnId, reasons: TextRef }` — не прошло |
| `run.status` (`journal.ts`) | `completion.kind` `"proposed" \| "whole" \| "rejected"`, только в журнале разбиения; `completedAllowed` для него — последний ход `decompose` и запись `proposed` или `rejected` либо ответ `whole` |
| `decide()` (`cycle.ts`) | ветка разбиения, до проверки предложенных команд: нет хода → ход `decompose`; последний `rejected`, отказов 1 → ход `decompose` с причинами; отказов 2 → `completed rejected`; `proposed` или `whole` → `completed`; вопрос → пауза `awaiting_answer`, ответ → ход `decompose` с ответом |
| `completion()` (`cycle.ts`) | то же для этого вида |
| `proposesChecks` (`cycle.ts`) | `false` для `kind: "decomposition"` |
| песочница лида | как у хода `plan` |

Старые сборки (1.5.16–1.5.20) видят журнал разбиения как журнал новой версии: только просмотр, остановка отклонена,
текст цели не показан (как журнал разрешения C3 §7.2). Проверяет E0.

### 3.3. Ответ лида

JSON-схема хода `decompose`:

```json
{ "tasks": [ { "id": "S1", "title": "…", "text": "…", "criteria": ["…"], "dependsOn": [], "covers": ["R1", "R2"] },
             { "id": "S2", "title": "…", "text": "…", "criteria": ["…"], "dependsOn": ["S1"], "covers": ["R3"] } ],
  "whole": null, "question": null }
```

- `id` — `S1…S10`, уникальные;
- `title` — 1…200 знаков, уникальные в списке;
- `text` — 1…4000 знаков. Остальные 4000 из предела задачи (8000) — приписка приложения §6: требования родителя, которые
  подзадача закрывает (до 32 × 500 = 16000), обрезаются, чтобы весь текст уложился в 8000;
- `criteria` — 1…16 × 1…500 знаков;
- `dependsOn` — `id` этого списка;
- `covers` — `R<n>` родителя;
- `whole` — 1…2000 знаков или `null`; `question` — как у плана. Ровно одно из трёх: непустой `tasks`, `whole`,
  `question`.

### 3.4. Старт, слежение, восстановление

По образцу C3 (`startResolution`, `syncResolutions`):
- **Старт** — `startDecomposition` в manager, в очереди `canvasStore.change`. Свой путь, не `startOnLink` и не старт
  задачи:
  - без записи в `link.runIds`; владелец — пространство в `owners`. Удаление связи или карточек его не касается;
  - CLI и профиль — связи, которую ведёт автопилот, или (кнопкой) связи, на которой задача последний раз шла; нет такой —
    единственная связь пространства для этой папки; иначе отказ `no_link`;
  - отказы:
    - `task_active_run` — у задачи есть свой незавершённый запуск;
    - `decomposition_active` — у задачи уже идёт разбиение (кнопка и автопилот, два автопилота);
    - `has_subtasks` — у задачи есть неархивные подзадачи;
    - `deps_not_ready` — зависимости родителя не готовы так, как требует обычный старт;
    - `damaged`, `newer_version` — доска не читается;
  - обратно: ручной старт родителя (`taskOk`) отказывает `decomposition_active`, пока идёт его разбиение.
- **Слежение** — `syncDecompositions` в том же таймере manager (1,5 с), что `syncResolutions`, и при первом чтении доски
  после перезапуска:
  - `completed proposed` и у родителя нет `decomposedBy` этого запуска → создание §5;
  - остальные исходы только выводятся (§2.1), записи не нужны.
- **Перезапуск приложения посреди хода** — как у других запусков: `paused(recovered)`, на карточке
  `decomposition_paused`, человек продолжает в панели.
- **Stop** — `stopped`, родитель `decomposition_failed stopped`.

## 4. Проверка предложения (приложение)

Предложение принимается, только если:
- подзадач 2…10, поля в пределах §3.3;
- `dependsOn` ссылаются на `id` этого списка, без циклов;
- **каждое требование родителя `R1…Rn` покрыто** хотя бы одной подзадачей, и других `R` нет (принцип 9).

Проверка формальная, её делает сервис запуска по цели и ответу. Состояние доски (свой запуск родителя, подзадачи) он не
видит: его проверяет main при создании (§5.1), без хода лида. По смыслу требования родителя проверяет завершающий запуск
(§6), поэтому он обязателен.

Отказ — запись `decomposition.rejected` с причинами. Лид получает причины в следующем ходе; после второго отказа —
`completed rejected`.

## 5. Создание подзадач

Делает main, а не ход агента, после `completed proposed`:
- **одна запись `board.json`** (`change()`):
  - все подзадачи с `parentId`, `covers` и `dependsOn` по §2;
  - текст каждой подзадачи с припиской §6;
  - новый `dependsOn` родителя и `decomposedBy: runId`;
- `order` подзадач — между родителем и следующей задачей очереди, в порядке предложения;
- каждая подзадача получает следующий `T-n` пространства;
- **без повторов**: если у родителя `decomposedBy` равен этому `runId`, ничего не создаётся. Удалённые человеком
  подзадачи заново не появляются;
- **восстановление** — в `syncDecompositions` (§3.4), не в чтении доски: сбой между завершением запуска и записью доски
  ничего не теряет и не задваивает.

### 5.1. Когда создать нельзя

Запись не делается; родитель — `decomposition_failed` с деталью. Повторов нет: следующая попытка — «Разбить ещё раз».

| Условие в момент записи | Деталь |
|---|---|
| у родителя есть свой запуск | `parent_started` |
| у родителя есть неархивные подзадачи (созданы другим путём) | `has_subtasks` |
| родитель удалён или в архиве | `parent_gone` |
| доска `damaged` или `newer_version` | `board_unreadable` |
| задач на доске станет больше предела (`too_many_tasks`) | `too_many_tasks` |
| требования родителя изменились после старта разбиения (число `R` другое) | `requirements_changed` |
| `decompose` снят, пока шло разбиение | `not_marked` |

## 6. Текст подзадачи и завершающего запуска

Новых полей цели нет: приписки — в тексте задачи. Запуски подзадач и родителя остаются обычными запусками задач v2, их
читают все сборки.

- **Подзадача.** Текст = текст лида + приписка:
  ```
  Часть задачи T-1 «<название>». Закрывает её требования:
  R2 — <текст>
  R3 — <текст>
  ```
  Требования — дословно, пока весь текст ≤ 8000. Остальные обрезаются с «…»; номера `R` остаются все. Это контекст, а не
  требования подзадачи: принимается она по своим `criteria`.
- **Завершающий запуск родителя.** `goalFor` (и ручной старт с карточки, тот же сбор цели) добавляет к тексту родителя
  абзац:
  ```
  Подзадачи T-2, T-3, T-4 выполнены и влиты в итог доски. Проверьте требования этой задачи на текущем коде
  и доделайте только недостающее.
  ```
  Абзац — до 400 знаков (ключи подзадач перечисляются, пока помещаются, затем «и ещё N»). Поэтому отметка
  `decompose` в форме требует текст ≤ 7600; длиннее — отказ `text_too_long` с подсказкой. Лид планирует сам, проверяющий
  проверяет требования T-1 дословно (принцип 4).

Поля цели `part`/`parts` (отдельный блок в запросе) — позже, если приписки в тексте не хватит.

### 6.1. По режимам работы

| Режим | Подзадачи | Родитель |
|---|---|---|
| «Отдельная копия» или worktree, автопилот | параллельно, до N сразу, от итога доски (C1, C2) | от итога доски, где влиты все неархивные подзадачи |
| «Отдельная копия» без автопилота | человек запускает и объединяет каждую («Объединить», C1) | стоит `waits_merge`, пока подзадачи не в итоге доски |
| «Папка проекта» | по одной (`autopilotStep`), в папке проекта | после последней подзадачи, в папке проекта |

Разбиение во всех режимах идёт в отдельной копии (§3.1).

Конфликт объединения между параллельными подзадачами — обычный конфликт объединения: его разрешает человек или агент по
настройке «Конфликты» (C3).

## 7. Автопилот

После C3/C4 весь учёт автопилота идёт по `taskId` фактов. У запуска разбиения `goal.task` нет, поэтому он встраивается
отдельно в каждое место.

**Факты.** В `RunTaskFacts` новое поле `decompositionOf?: string` — `taskId` родителя (из `decomposition.taskId`
цели), и значения `completion` `proposed` / `whole` / `rejected`. `taskId` у такого факта пустой: в запуски задачи он
не попадает. Вид доски (`board()` в manager) пропускает факты с `taskId`, `taskKey` или `decompositionOf`.

**Свой список.** `splits` в записи автопилота, как `agents` у C3: идущие запуски разбиения, которые начал автопилот.

| Место | Сейчас | С разбиением |
|---|---|---|
| места (`busy` в `autopilotParallelStep`) | факты задач места в `SLOT` + `merges…agent.pending` | + факты с `decompositionOf` задачи этого места в `SLOT` |
| бюджет запусков (`used.runs`) | `started` + `agents` | + `splits` |
| минуты (`used()` → `activeMs`) | записи `started` и `agents`, паузы `limitTurns` не в счёт | + записи `splits`, их ходы, оборванные лимитом, — в `limitTurns` |
| лимит провайдера (`limitedRuns`) | факты задач места + `resolutionLimits` | + `decompositionLimits` (по образцу `resolutionLimits`): свои разбиения на паузе с `providerLimit`, ключ — ключ родителя |
| продолжение после сброса (`resume`) | свои запуски из `started` и `agents` | + `splits`; счётчик «3 подряд» сбрасывается по завершённому ходу, как у остальных |
| последовательный шаг (`autopilotStep`) | смотрит только `last` из `started` | сначала свой идущий разбиение-запуск: идёт или ждёт ответа → `wait run`; на лимите → `limitStep`; иначе как ниже |

**Шаг `decompose`** — в обоих шагах, после `take`/`merge` и проверки лимита, перед стартом обычной задачи:
- берёт первую по порядку задачу места с `decompose: true`, без `decomposedBy`, без своего запуска и **без единого
  разбиения**, с зависимостями, готовыми так, как требует обычный старт (`depsWait === null`, в итоге доски);
- нужно свободное место и бюджет запусков, как для задачи;
- повтор разбиения автопилот не делает никогда: «Разбить ещё раз» — команда человека (§2.1).

**`next` и `nextTask`** не берут родителя с `decompose: true`, пока у него нет `decomposedBy` и последнее разбиение не
`whole`, а также родителя в состояниях `decomposition_failed`, `decomposition_paused`, `subtasks_gone`.

**После `proposed`** подзадачи создаются (§5), автопилот берёт их следующим шагом (решение владельца 2).

**Остановки** — как у своих запусков задач:
- свой разбиение-запуск `failed`, `stopped`, `completed rejected` или создать нельзя (§5.1) — автопилот выключается с
  новым кодом `decomposition_failed` (+ деталь), как `run_failed`;
- на паузе не по вопросу и не по лимиту — выключается, как `halt` у задач;
- вопрос лида — ждёт, как `waits_answer`;
- чужое разбиение (кнопкой) в этих состояниях автопилот не выключает: он не берёт этого родителя и идёт дальше.

**Бюджет общий** для разбиения, подзадач и завершающего запуска. Если он кончился посреди цепочки — обычная остановка
«бюджет». Подзадачи и родитель остаются как есть; следующее «Запустить доску» продолжит.

## 8. Пожелания проверяющего → задачи (после E)

Решение владельца 4 («Сделать задачей» — кнопка для человека) остаётся в силе, но с разбиением не связано. Это отдельный
шаг E5, своим PR после E4, со своим полем `origin: { kind: "finding", runId, findingId }` и своими фикстурами отката.
Содержание — как в ревизии 2:
- `title` — из `problem`;
- `text` — из `problem`, `evidence`, `closeWhen` со строкой «Из пожелания F3 запуска T-2»;
- `criteria` — `[closeWhen]`;
- дубликат по `(runId, findingId)` не создаётся;
- у закрытого пожелания кнопки нет.

## 9. Совместимость и откат

- **`board.json`** v1 с новыми полями (`decompose`, `decomposedBy`, `parentId`, `covers`). Старые сборки (1.5.16–1.5.20)
  видят подзадачи и родителя как обычные задачи с зависимостями; приписки — обычный текст.
  - Родитель с `decompose` без подзадач старая сборка выполнит целиком. После возврата на новую сборку у родителя есть
    свой запуск: его разбиение не создаёт подзадачи (`parent_started`).
  - Подзадача в архиве в старой сборке держит родителя (там архивная зависимость держит всегда): родитель ждёт
    навсегда. Выход — убрать её из зависимостей родителя вручную или вернуться на новую сборку.
- **Журнал разбиения** — конверт v3 по образцу C3: старые сборки показывают его только для просмотра и не дают
  остановить. Перед откатом — дождаться конца разбиений (как с запусками разрешения в `release/1.5.20/INSTALL.md`).
- **Запуски подзадач и родителя** — обычные запуски задач v2, без новых полей цели.
- **ROADMAP «Перед публикацией»:** журнал разбиения (v3, `minReaderVersion` 3, назначение `decompose`, записи
  `decomposition.*`) и новые поля задачи входят во внешнее ревью вместе с журналами C.
- **Результат E0 (2026-10-19): модель данных не меняется.** `scripts/e-rollback-fixtures.mjs`, упакованные 1.5.16,
  1.5.17, 1.5.18, 1.5.19 и 1.5.20 — 12/12 каждая. Доска с T-1 (`decompose` без подзадач), T-2 (`decomposedBy`, зависит

  Не проверено: что архивная подзадача держит родителя в старой сборке (по коду `depsOf` — держит, пункт выше).

## 10. Интерфейс

- **Форма задачи:** галочка «Разбить на подзадачи». Её нет у подзадачи, и она недоступна, если у задачи есть свой
  запуск или неархивные подзадачи. Текст длиннее 7600 при отметке — отказ (§6).
- **Карточка родителя:** причины и действия по §2.1.
  - «Открыть разбиение» открывает панель запуска разбиения (как панель запуска разрешения C3: её нет в списке, она
    открывается по `runId`). Предложение видно на вкладке «План»: список подзадач с зависимостями и покрытием `R`.
    Причины отказа — в ленте.
  - После создания на карточке строка «подзадачи: k из n в итоге доски», ключи подзадач (по нажатию — к карточке) и
    пометки §2.1.
- **Карточка подзадачи:** «часть T-1» (по нажатию — к родителю); в подробностях — «закрывает R2, R3 задачи T-1»;
  пометка «родитель в архиве».
- **Окно автопилота:** «разбивает T-1 на подзадачи»; после остановки — причина `decomposition_failed`.
- **Уведомления** (`notify.ts`, ключи в `orch.notified.v1`, при включённой «Доске» и окне не в фокусе, первое
  появление только записывается):
  - `split:<runId>` → «Разбиение T-1 не удалось» — один раз на запуск, в состоянии `decomposition_failed`;
  - вопрос лида — уведомление ожидания ответа, как у запусков, «Лид спрашивает: разбиение T-1»;
  - значок Dock считает разбиения, которые ждут человека (вопрос, `decomposition_failed`, `decomposition_paused`).

## 11. Решения владельца (2026-10-19)

1. **Порядок:** E — после C4.

- 3 подзадачи по 4 хода (план, исполнение, проверка, финальная проверка): 12;
- завершающий запуск: 4;
- итого около 18, остальное — запас на отказ, повтор и замечание проверяющего.

## 13. Как сделано

### E1 — журнал и запуск разбиения

- Цель: `Goal.decomposition {taskId, key, base}`, проверка `checkDecomposition` рядом с `checkResolution`. Кроме §3.1
  отвергаются `prepare` и `finish`; `commands` обязаны быть заданы и пусты. `resolution` и `decomposition` исключают
  друг друга. По IPC поле не приходит: `parseGoal` берёт только известные ключи. Старт из доски (E2) передаёт
  `commands: []` явно и не задаёт `mode`, иначе профиль добавит команды или подготовку.
- Журнал: тот же конверт v3, что у разрешения C3 (`minReaderVersion` 3, правила v2), `run.created` с `kind:
  "decomposition"`; `isDecompositionJournal` рядом с `isResolutionJournal`; `RunState.kind`. В журнале разбиения
  допустимы только ходы `decompose`, а ход `decompose` — только в нём; план в нём — конфликт.
- **Отступление от §3.2:** кроме `decomposition.proposed` и `decomposition.rejected` есть третья запись
  `decomposition.whole {turnId, why}`. Без неё чистый цикл не видит ответа «выполнять целиком». Каждая запись — ответ
  последнего завершённого хода `decompose`, одна на ход.
- `run.status` v3 принимает `completion.kind` `proposed` / `whole` / `rejected`. `completedAllowed` для журнала
  разбиения — своя ветка: вид завершения должен совпадать с ответом последнего хода (`rejected` — не меньше двух
  отказов). Правило «`no_checks` ⇔ ноль команд» в `textsConflict` к нему не применяется. В обычном журнале разрешения
  эти виды отвергаются при воспроизведении.
- Цикл: ветка разбиения в `decide()` сразу после паузы вопроса; `proposesChecks` для неё ложно; `completion()` не
  вызывается — `complete()` пишет основание `{kind, turnId, ref}`.
- Ход: роль всегда лид; схема `decompose` в подмножестве без `pattern` и `minItems`, поэтому id подзадач — перечень
  S1..S10, а «хотя бы один критерий» и «ровно одно из tasks / whole / question» проверяют `reportProblem` и
  `splitViolations` (§4). Отказ возвращает причины лиду в следующем ходе.
- Факты задачи доски (`completion`) по-прежнему только `confirmed` / `no_checks`: запуск разбиения не запуск задачи.
- Тесты: `tests/orchestration-journal-split.test.mjs` (7), `tests/orchestration-split-run.test.mjs` (11).

### E2 — подзадачи на доске

- Поля задачи (§2): `decompose` хранится только как `true`; `isTask` принимает новые поля, если они есть, и проверяет
  их форму. Задачу с `parentId` и `decompose` из файла не отвергает: ручная правка не откладывает доску, отказ — при
  создании и правке. Отметка при тексте длиннее 7600 — `text_too_long`. «Выполнить целиком» (`decompose: false`)
  снимает и `decomposedBy`; при неархивных подзадачах — `has_subtasks`, во время разбиения — `decomposition_active`
  (manager).
- Создание (§5): `boardStore.split(parentId, runId, plan)` — одна запись со всеми отказами §5.1 кодом отказа хранилища.
  Тот же `runId` второй раз ничего не пишет. `parent_started` и `board_unreadable` проверяет manager.
- §2.2: помощник `heldDeps` — архивная подзадача не держит своего родителя — в `boardStatuses`, `startBase`, `baseOf`,
  `nextTask` и отборе `next` у `autopilotParallelStep`; `taskOk` идёт через `boardStatuses`. «Родитель в архиве» — E3.
- Тексты (§6): `subtaskText`, `taskText`; `goalFor` получает задачи доски (`tasks`), ручной старт с карточки — тот же
  `taskText`.
- Состояния (§2.1): `parentStatus` в `boardStatuses` — только пока у родителя нет своего запуска. Факты запуска
  разбиения: `decompositionOf`, `split` (вид завершения — отдельно от `completion`, которое остаётся у запусков задач;
  отступление от формулировки §7), `splitFailed`.
- Старт и слежение (§3.4): `startDecomposition` (команда `board:decompose`), `watchDecompositions` /
  `syncDecompositions` — свой таймер 1,5 с, запускается стартом и первым чтением доски после перезапуска.
- Отступления:
  - **Связь не выбирается**: как у разрешения C3, CLI берутся из окружения проекта; отказа `no_link` нет (ключ текста
    есть, его никто не шлёт).
  - **Отказ создания §5.1 хранится в памяти** (`splitFailed`): после перезапуска условия проверяются ещё раз, при тех же
    условиях код тот же.
  - **«Пропустить» у подзадачи** даёт родителю `waits_head` с её ключом (правило C2 для зависимости вне итога доски), а
    не `waits_merge`, как писал §2.2. Правила C не менялись.
  - Разбиение, чьё предложение ещё не стало подзадачами, тоже `decomposition_active` для нового старта.
  - Удалённый с доски родитель: слежение его не видит, `parent_gone` — только у архивного.
  - Защита автопилота до E3: `nextTask` и `next` не берут родителя с отметкой без `decomposedBy`, кроме ответа `whole`.
  - Для теста паритета i18n добавлены ключи `orchError_*` всех кодов отказа (`board_unreadable`, `parent_gone`,
    `parent_started`, `requirements_changed`, `not_marked`) сверх таблицы §10.
- Тесты: `tests/orchestration-board-split.test.mjs` (11), `tests/orchestration-board-split-manager.test.mjs` (6).
