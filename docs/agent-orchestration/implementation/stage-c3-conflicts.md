# Этап C3: конфликт объединения разрешает агент

**Статус: ревизия 3, после двух кругов ревью, 2026-10-19. Реализовано** в ветке `feat/c3-agent-conflicts` (2026-10-19);
отличия реализации от текста — в §13. Документ уточняет подэтап C3 из
[этапа C](stage-c-parallel.md) (§1 сценарий 3, §2.1, §4.3, §5, §6.2, §7, §9). Отличия от этапа C собраны в §11.

Ревизия 1 предлагала вести ходы агента прямо в журнале объединения. Ревью (скептик, критик) показало, что это
нереализуемо без переделки журнала: у файла было бы два писателя, у цикла не было бы цели и `workspace.created`, план
без хода лида не проходит разбор. Ревизия 2 выносит ходы в **отдельный запуск разрешения** (§2). Ревизия 3 —
исправления второго круга: поле `resolution` вместо `task`, слежение и восстановление, версия конверта отдельно от
правил, команда проверки маркеров, lock-файлы и повторы — человеку, перенос через `applyTreeToCopy`.

Опирается на:
- решение владельца 3 этапа C: с C3 конфликт по умолчанию поручается агенту, остаток риска семантического конфликта
  принят;
- решение 7: запуски объединения — журнал v3 (`minReaderVersion` 3);
- код 1.5.19: `boardMerge.ts` (запуск объединения без ходов), цикл v2 (`cycle.ts`, `orchestrationService.ts`,
  `journal.ts`, `store.ts`), автопилот доски (`autopilotParallelStep` в `taskBoard.ts`, `boardAutopilot.ts`).

## 0. Что есть сейчас (1.5.19)

- **Запуск объединения** — свой небольшой движок в `boardMerge.ts`. Он пишет журнал v3 сам, без блокировки:
  читает файл и дописывает строку (`append`). Записи: `run.created` → `merge.prepared` → `merge.checked` →
  `merge.resolved` → `merge.committed` → `merge.advanced` и `run.status` в своей форме.
- Сама 1.5.19 этот журнал как запуск не воспроизводит. `records()` разбирает его как «более новую версию»: только
  цепочка хешей. Состояние собирает `stateOf()` из записей `merge.*` и `run.status`.
- **Конфликт git** — пауза `merge_conflict`. **Проверки, упавшие дважды,** — пауза `merge_checks_failed` с пометкой
  «возможна помеха». В обоих случаях решает человек: правит копию и нажимает «Готово, проверить», или «Пропустить».
- **Механическое условие для человека** уже есть в `resolve()`: маркеры в конфликтных файлах — отказ; файлы вне
  конфликта, изменённые разрешением (`outside`), — подтверждение «Да, я менял и их». Затем `finish()`: зависимости,
  подготовка, проверки (с одним повтором), коммит, вершина.
- **Автопилот:** любое объединение на паузе — ожидание человека (`person = "merge"`, `taskBoard.ts:532`). Объединения
  не стоят на связях и в слотах не считаются (`busy` — только запуски задач).

## 1. Что увидит человек

T-1 и T-2 правили одну функцию в `src/auth.ts`. T-1 уже в итоге доски, при вливании T-2 git сообщает конфликт.
1. Настройка доски «Конфликты: поручать агенту» (по умолчанию). Объединение T-2 не встаёт на паузу. Приложение
   заводит запуск разрешения: исполнитель правит конфликт, проверки, проверяющий.
2. На доске у T-2: «Готово · объединяется: агент разрешает конфликт в src/auth.ts». На карточке исполнителя связи —
   строка «Объединение T-2 · Claude разрешает конфликт». По нажатию открывается панель запуска разрешения: «План»,
   «Лента», «Действия», как у обычного запуска.
3. Разрешение прошло — объединение переносит его в свою копию, проверяет механическое условие, прогоняет
   обязательные проверки и двигает вершину. На карточке T-2: «Готово · в итоге доски».
4. Не прошло — пауза объединения для человека: «Готово · не объединено: конфликт в src/auth.ts — агент не
   справился (<причина>)». Копия объединения — в том виде, в каком её оставил агент, если его разрешение дошло до
   конца; иначе как оставил git. Кнопки: «Открыть папку», «Готово, проверить», «Поручить агенту ещё раз»,
   «Пропустить».

При настройке «Решать мне» всё как в 1.5.19, плюс кнопка «Поручить агенту» на паузе конфликта.

## 2. Устройство: отдельный запуск разрешения

**Запуск объединения** (`boardMerge`) остаётся как есть и остаётся единственным писателем своего журнала. Он
отвечает за копию объединения, механическое условие, проверки, коммит и вершину.

**Запуск разрешения** — отдельный запуск оркестрации со своим журналом, своим Writer, своей целью, своей рабочей
копией. Его ведёт обычный controller цикла v2. Объединение ждёт его и читает только его итог.

### 2.1. Как начинается

1. Конфликт (`merge.prepared` с `conflicts`) или дважды упавшие проверки, настройка «поручать агенту», выполнены
   условия старта (§6). Иначе — пауза для человека, как в 1.5.19.
2. `boardMerge` в очереди git проекта:
   - снимает дерево копии объединения как есть — с маркерами конфликта (`snapshotCopyTree`);
   - собирает из него коммит с родителем — ожидаемой вершиной (`commitSnapshot`) и публикует его существующим путём
     контрольных точек: `publishRef(mergeWs, "conflict-<attempt>")` → `refs/canvastty/<mergeRunId>/conflict-<attempt>`
     (только создание, имя проходит `REF_NAME`). Ссылки живут, как ссылки запусков: удаляются вместе с запуском;
   - пишет `merge.agent { attempt, reason: "conflict" | "checks", resolutionRunId, base: <коммит> }`. Статус
     объединения остаётся `running`.
3. Main стартует запуск разрешения операцией `startResolution` в очереди `canvasStore.change`. Это свой путь, не
   `startOnLink` и не старт задачи:
   - без записи в `link.runIds`, владелец — пространство в `owners`, как у объединения (этап C §5.3). Удаление связи
     или карточек его не касается;
   - мимо `taskOk` и `checkBase` (они принимают базу только как вершину или ветку зависимости и только в v2): своя
     проверка — база равна `merge.agent.base` этого объединения; `createWorkspace` получает `from` напрямую;
   - рабочая копия — «отдельная копия» от коммита `base`. В ней нет незавершённого `git merge`: маркеры — обычный
     текст файлов.

### 2.2. Как ведётся

Обычный цикл v2 без лида: план пишет приложение (§3), исполнитель, проверки, проверяющий по этапу, финальное ревью
проверяющего. Ход с назначением `plan` в запуске разрешения не делается (§5).

### 2.3. Как заканчивается

**Слежение.** Ожиданием владеет manager: он подписан на запуск разрешения (`handle.onChange`, как на запуски задач)
и при каждом изменении статуса, а также один раз при старте процесса, читает его итог (`readRun`) и передаёт в
`boardMerge.resolutionEnded(mergeRunId, итог)`. Сам `boardMerge` чужие журналы не разбирает.

**Восстановление.** `boardMerge.recovered()` не трогает объединение, у которого последний `merge.agent` без
последующего `merge.resolved`: оно ждёт разрешения, даже если процесс, который его вёл, кончился. То же для
`paused(recovered)` поверх такого `merge.agent` (его пишет 1.5.17–1.5.19 после отката): C3 продолжает ждать
разрешения. Запуск разрешения восстанавливается как любой запуск (`paused(recovered)` / `outcome_unknown`), сам ничего
не продолжает.

- **`completed` с `completion: confirmed`.** В очереди объединения `boardMerge`:
  1. переносит дерево последней контрольной точки разрешения в копию объединения: `applyTreeToCopy(ws, <дерево
     base>, <дерево разрешения>)` (`workspace.ts:996`). Он требует, чтобы копия была ровно деревом `base`, и
     отказывает на неотслеживаемых файлах. Отказ — пауза `merge_agent_failed`, `copy_changed`. Поэтому на время
     разрешения «Открыть папку» объединения скрыта;
  2. сверяет: снимок копии равен дереву разрешения;
  3. механическое условие, как в `resolve()`: маркеры (§4), `outside` против `merge.prepared.auto`;
  4. пишет `merge.resolved { by: "executor", tree, outside, resolutionRunId }`;
  5. вызывает `finish()` как есть: зависимости, подготовка, обязательные проверки на дереве слияния, коммит, вершина.

  Проверки повторяются в копии объединения сознательно. «Готово» объединения решают только его собственные записи
  `merge.checked`, а не чужой журнал, поэтому `lastChecked` при сбое между `merge.committed` и `merge.advanced` даёт
  `confirmed`. Цена — время одного прогона проверок, без вызовов модели.
  - Если эти проверки упали (дважды, как всегда), агенту второй раз автоматически не поручается: пауза
    `merge_agent_failed`, `checks_after`. Автоматически агенту поручается только объединение без предыдущего
    `merge.agent`; дальше — кнопкой человека.
- **Любой другой конец** (`stopped`, `failed`, пауза, которую человек не снимает, `completed` без проверок) — §5.

## 3. Цель запуска разрешения

Цель собирает приложение. Это обычная цель v2 (`GoalInput`) плюс план приложения:

| Поле | Значение |
|---|---|
| `text` | задание (ниже) |
| `criteria` | требования (§3.1) |
| `commands` | обязательные команды проверки проекта + проверка маркеров (§4) |
| `workMode` | `"copy"`, `base` — коммит конфликта (§2.1) |
| `mode` | `"autopilot"`; `reviewPlan: false` |
| `access`, `models`, `prepare` | из профиля проекта на момент старта, как у задач автопилота (снимок B §5.1) |
| `limits` | `turns` 8, `roundsPerStage` 3, `replans` 0, `runMs` 40 минут |
| `resolution` | `{ mergeRunId, taskId, key }` — для показа на доске. **Не** `task`: с `goal.task` запуск стал бы текущим запуском T-2 (`metaOf`, `manager.ts:748`; `boardStatuses`), T-2 потеряла бы «в итоге доски», зависимые бы встали, автопилот забрал бы ветку разрешения. `metaOf` и `boardStatuses` поле `resolution` не читают |
| `language` | язык интерфейса |

`createdAt` — момент старта запуска разрешения, поэтому `runMs` не включает ожидание слота и паузы объединения.

**Задание исполнителю** (конфликт git):
«Разрешите конфликт слияния в <файлы>. Сохраните требования обеих сторон: задачи <T-2> и итога доски. Не удаляйте и
не откатывайте чужие изменения. Маркеры конфликта (`<<<<<<<`, `>>>>>>>`) не должны остаться. Коммиты не нужны:
приложение соберёт коммит само».

**Задание** (семантический конфликт): «После объединения <T-2> с итогом доски падают проверки: <команды и хвост
вывода>. Исправьте, сохранив требования обеих сторон. Падение может быть помехой другой задачи (занятый порт). Если
так — задайте вопрос, ничего не меняя».

### 3.1. Требования

Одна функция `mergeRequirements(head, task, paths)` для обоих видов конфликта:
1. `paths` — конфликтные пути (конфликт git) или пути, изменённые T-2 от базы её запуска до её коммита результата
   (семантический).
2. Источники по порядку:
   - запуск задачи T-2, который вливается (`merge.task.runId`): его `criteria`;
   - задачи, уже влитые в вершину, в порядке их объединений (от старых к новым), если их изменения (от базы запуска
     до коммита результата, `merges.changed`) пересекаются с `paths`: `criteria` запуска, который вливался;
   - требование приложения: «В файлах <конфликтные пути> нет маркеров конфликта» (только конфликт git). Предел текста
     требования — 500 символов: пути, которые не вошли, — «и ещё N файлов (список — в задании)».
3. Одинаковый текст — один раз (первое вхождение).
4. Предел цели — 32. Требование приложения и требования T-2 всегда входят. Остальные — по порядку, пока есть место.
   Задачи, чьи требования не вошли, перечислены в задании: «Требования T-4, T-5 — в их запусках». В «Плане» это
   видно.

Сторона, у которой нет запуска (первая вершина из рабочей папки), требований не даёт: от неё в задании только «не
откатывайте изменения итога доски».

### 3.2. План приложения

Запуск разрешения начинается с плана, который пишет приложение. План в форме `PlanReportV2`:
- один этап, задание — из §3;
- условие `change` «Конфликт разрешён с сохранением требований обеих сторон», покрывает все R<n>; отмечает
  проверяющий;
- условия `check` — по одному на каждую команду из `commands`.

Запись: `plan.recorded { by: "app", version: 1, plan, firstStage: 1, stageCount: 1, conditionsAssigned }` без
`turnId`. Такой план бывает только в журнале запуска разрешения (§7.2).

## 4. Механическое условие

- **Маркеры.** В `commands` запуска разрешения последней строкой — проверка приложения:
  `! grep -sIE '^(<{7}|>{7}) ' -- '<путь 1>' '<путь 2>' …` (пути в одинарных кавычках, с экранированием). Она идёт,
  как все команды цели, в оболочке входа (`shellRegistry`, `-ilc`), а не в песочнице. Найдены маркеры — код 1, проверка
  упала. Нет маркеров или файла нет (конфликт изменение/удаление разрешён удалением) — проверка прошла.
  - Упавшая проверка ведёт цикл так же, как любая: ревью проверяющего с её выводом, затем ход исполнителя. Каждый
    промах по маркерам стоит вызова проверяющего и тратит `roundsPerStage`. Новых механизмов в цикле не нужно.
  - Предел цели — 16 команд, 1000 символов на строку. Профиль с 16 командами — агенту не поручается (§6). Пути,
    не вошедшие в 1000 символов, — вторая строка проверки, если есть место; нет места — агенту не поручается.
  - После переноса в копию объединения `boardMerge` повторяет проверку маркеров (как `resolve()`).
- **Конфликт без маркеров** (бинарный файл, изменение/удаление, переименование). Путь, не изменённый разрешением,
  попадает в `outside`, как у человека.
- **Файлы вне конфликта** (`outside`). Это не отказ: правильное разрешение иногда требует правки рядом.
  - Проверяющий видит их в каждом ревью: к заданию ревью приложение добавляет diff против коммита конфликта первой
    попытки (`conflict-1`: это и есть автоматическое слияние `merge.prepared.auto`, опубликованное в проекте, поэтому
    оно доступно копии любой попытки) и список `outside`. Удаление или откат изменения одной из сторон без замены — блокирующее
    замечание.
  - После переноса `outside` пересчитывается по дереву и пишется в `merge.resolved`.
  - Подтверждения человека не нужно. Этим C3 отличается от пути человека (§11).

## 5. Когда агент не справился

| Что случилось в запуске разрешения | Объединение | Причина паузы объединения, `detail` |
|---|---|---|
| `limit_reached` (`turns`, `roundsPerStage`, `runMs`, `replans`) | пауза | `merge_agent_failed`, `limit:<вид>` |
| запрос проверяющего `replan` (при `replans` 0 — `limit_reached replans`) | пауза | `merge_agent_failed`, `replan` |
| `stopped` (человек остановил запуск разрешения) | пауза | `merge_agent_failed`, `stopped` |
| `failed` | пауза | `merge_agent_failed`, `failed` |
| пауза сбоя (`external_failure`, `environment_error` и т. п.): человек может нажать «Продолжить» в запуске разрешения | ждёт; объединение остаётся `running`, автопилот — ждёт человека | — |
| вопрос исполнителя, разрешение, решение человека | ждёт; автопилот: ждёт человека | — |
| `completed` без проверок (`no_checks`) | не бывает: `commands` всегда содержат проверку маркеров | — |
| механическое условие после переноса не прошло (маркеры) | пауза | `merge_agent_failed`, `markers` |
| копия объединения изменилась во время разрешения, перенос отказал | пауза | `merge_agent_failed`, `copy_changed` |
| проверки после переноса упали дважды | пауза | `merge_agent_failed`, `checks_after` |

- На паузе `merge_agent_failed` человек может: доделать копию сам («Готово, проверить» — путь 1.5.19), «Поручить
  агенту ещё раз» или «Пропустить».
- Человек может в любой момент остановить запуск разрешения из его панели: это строка `stopped`.
- **Повторная попытка** — новый запуск разрешения со своими лимитами, `merge.agent { attempt: n+1 }`. База — снимок
  копии объединения на момент повтора (там может быть частичное разрешение человека). Бюджет запусков автопилота:
  каждая попытка — запуск.
- **Кнопки «Вернуть лиду» в запуске разрешения нет.** controller не делает ход `plan`, если план записан
  приложением.

## 6. Условия старта, права, слот, бюджет

**Агенту не поручается** (сразу пауза для человека, как в 1.5.19):
- обновление итога от HEAD (`source: "head"`, решение 13 этапа C): у него нет задачи и требований;
- проект без сохранённых команд проверки или с пустым списком: проверок нет, защищает только проверяющий —
  мало для изменения чужого кода;
- объединение задачи, стартовавшей не от вершины (§4.5 этапа C), — у неё могут быть лишние конфликты;
- среди конфликтных файлов есть lock-файл зависимостей (`package-lock.json`, `composer.lock` и прочие из профиля
  подготовки): копия с маркерами в нём не клонирует зависимости и роняет подготовку до первого хода;
- в профиле 16 команд проверки или пути не помещаются в проверку маркеров (§4);
- автоматически — второй раз для того же объединения (§2.3).

**Чьи настройки и CLI.** Связь даёт только настройку «Конфликты»: в автопилоте — связь, которую он ведёт; при
ручном «Объединить» — связь, на которой шла задача T-2 (нет записи автопилота — само не поручается, только кнопкой).
CLI исполнителя и проверяющего — как у запусков проекта (`deps.native(project)`, `manager.ts:337`), с моделями ролей
из настроек проекта.

**Права** — профиль проекта на момент старта, как у задач. Снимок настроек автопилота (B §5.1) сверяется перед
стартом. Права не шире, чем у запусков задач того же профиля.

**Слот.** Запуск разрешения, пока он не завершён, занимает слот места (§2.1 этапа C). Автопилот считает его из
`head.merges` (объединение с `merge.agent` и незавершённым запуском разрешения), а не из связей и facts. Нет
свободного слота — объединение ждёт слота: `run.status paused` с причиной `merge_waits_slot`. Это **не** ожидание
человека: в `autopilotParallelStep` (`taskBoard.ts:532`, сейчас любая пауза объединения — `person = "merge"`) эта
причина исключается. Автопилот показывает «Объединение T-2 ждёт места», новых задач не берёт, пока место не займёт
разрешение. 1.5.17–1.5.19 после отката покажут её как ожидание человека.

**Папка проекта.** Пока объединение ждёт разрешения, запуск в режиме «папка проекта» не стартует (`folder_busy`):
запуск разрешения — запуск проекта, правило §3.1 этапа C. Это видно на доске: «Папка проекта занята: идёт
объединение T-2». Освободилось место —
автопилот стартует разрешение сам. Без автопилота (ручное «Объединить») слот не ждут: правило ручных запусков
(решение 12, очередь) — то же.

**Бюджет.** Каждая попытка разрешения — один запуск бюджета, её рабочие минуты — в минуты (§7 этапа C, решение 14).
Бюджет исчерпан — пауза для человека с причиной `merge_budget`.

**Вопросы и разрешения** исполнителя и проверяющего — в панели запуска разрешения. Значок Dock и уведомления
считают их, как у обычного запуска.

## 7. Хранилища

### 7.1. `board.json`

Без изменения версии. Поле записи автопилота связи `autopilot[linkId].conflicts`: `"agent" | "person"`, отсутствует —
`"agent"`. Оно описано в §5.1 этапа C. Сборки 1.5.15–1.5.19 сохраняют ключ при других записях и теряют при смене
бюджета этой связи (`boardStore.ts:216`). После потери — значение по умолчанию.

### 7.2. Журналы

**Журнал объединения (v3)** — пишет только `boardMerge`, как в 1.5.19. Новое:
- `merge.agent { attempt, reason, resolutionRunId, base }`;
- `merge.resolved` — значение `by: "executor"` и поле `resolutionRunId`;
- причины паузы `merge_agent_failed` (с `detail`), `merge_waits_slot`, `merge_budget`.

`stateOf()` 1.5.17–1.5.19 читает `run.status` и `merge.*` по известным полям, незнакомые записи пропускает. Это
нужно проверить до реализации (§10, шаг 1).

**Журнал запуска разрешения** — v3, `minReaderVersion` 3, цель `kind: "resolution"`. Всё — записи v2 по правилам v2,
кроме одного: `plan.recorded` с `by: "app"` без `turnId`.
- Почему не v2: план без хода лида — запись, которую разбор v2 в 1.5.8–1.5.19 отвергнет, и журнал станет
  «повреждённым». `minReaderVersion` 3 даёт старым сборкам «создан более новой версией, только просмотр».
- Первая запись: `run.created { goal: TextRef, kind: "resolution" }` (новый ключ; схема v2 — ровно `goal`,
  `journal.ts:449`). Признак `kind` — в записи, а не в texts, чтобы разбор остался чистой функцией над буфером.
  1.5.19 из-за лишнего ключа не покажет текст цели в просмотре запуска более новой версии (`newerGoal`); на доске
  запуск всё равно виден через объединение.
- **Версия конверта и правила разведены.** У состояния два поля: `envelope: 3` (что пишется в `v` каждой строки и
  проверяется как `minReaderVersion` первой записи) и `rules: 2` (по каким правилам воспроизводится). Writer пишет
  `v: envelope`. Около 40 проверок `version === 2` (`orchestrationService.ts`, `journal.ts`, `store.ts`, `findings.ts`,
  `cycle.ts`) читают `rules`; список — в PR, тест на каждую группу.
- `plan.turnId` становится `string | null`, все места чтения перечисляются в PR. Другие журналы v3 — по-прежнему
  «более новая версия».

### 7.3. Совместимость

| Сборка | Объединение с `merge.agent` | Запуск разрешения |
|---|---|---|
| C3 | полностью | полностью |
| 1.5.17–1.5.19 | как объединение: статус и пометки по `run.status` и `merge.*`; при `running` после перезапуска — `paused(recovered)`, человек: «Готово, проверить» или «Пропустить» | «создан более новой версией», только просмотр, ничего не держит |
| 1.5.8–1.5.16 | «создан более новой версией» | то же |

После отката на 1.5.19 и «Готово, проверить» там (`merge.resolved by person` поверх `merge.agent`) C3 после
возврата продолжает объединение как решённое человеком; запуск разрешения, если он не закончился, остаётся на паузе
и в объединение не переносится. Без действий человека 1.5.19 оставит `paused(recovered)`: C3 после возврата ждёт
разрешения дальше (§2.3, «Восстановление»).

## 8. Интерфейс

- **Окно автопилота:** «Конфликты: поручать агенту / решать мне». Пояснение: «Агент правит отдельную копию; итог
  доски двигается только после проверок».
- **Пауза конфликта** («Решать мне») и `merge_agent_failed`: к «Открыть папку», «Готово, проверить», «Пропустить»
  добавляется «Поручить агенту» / «Поручить агенту ещё раз». Причина неудачи — строкой.
- **Карточка задачи:** «Готово · объединяется: агент разрешает конфликт в <файлы>», «Готово · объединение ждёт
  места», «Готово · не объединено: конфликт в <файлы> — агент не справился (<причина>)».
- **Карточка исполнителя связи** (§6, «Чьи CLI»): «Объединение T-2 · Claude разрешает конфликт» / «· ждёт вас».
  Нажатие открывает панель запуска разрешения. В списке запусков холста запуск разрешения не показывается, как
  объединение.
- **Уведомления:** «Объединение T-2 — агент не справился, решите» (вместо «конфликт, решите», если агент
  пробовал).

## 9. Автопилот

Изменения таблицы §8 этапа C:

| Событие | Исход |
|---|---|
| Конфликт или дважды упавшие проверки, «поручать агенту», агенту можно (§6), есть слот и бюджет | старт разрешения; автопилот ждёт («run») |
| То же, нет слота | `merge_waits_slot`; автопилот новых задач не берёт, ждёт («run») |
| То же, бюджет исчерпан | `merge_budget` — ждёт человека |
| Разрешение ждёт ответа или разрешения | ждёт человека; другие слоты работают |
| `merge_agent_failed` | ждёт человека, как пауза конфликта сейчас |

Пока объединение в эту вершину идёт или ждёт, другие объединения в неё не начинаются (одно за раз, как сейчас).

## 11. Отличия от этапа C

| Этап C | C3 | Почему |
|---|---|---|
| §4.3: «тот же запуск объединения продолжается ходами» | ходы — в отдельном запуске разрешения | один писатель на журнал; у цикла своя цель и копия |
| §5.2: план приложения и записи v2 — в журнале объединения | в журнале запуска разрешения (v3, `kind: "resolution"`) | то же |
| §4.3: изменение вне конфликта → режим семантического конфликта | `outside` — проверяющему, без подтверждения человека | проверяющий уже видит diff; это и есть путь «семантического» ревью |
| §4.3: «дальше обычный цикл A … лимиты» | лимиты — константы, `replans` 0, без лида | решение 7: лид может «разрешить» несуществующее |
| §6.2: строка на карточке исполнителя | та же, плюс правило «чья связь» при ручном пути | этап C его не задавал |
| — | обновление от HEAD, проект без команд, задача не от вершины — всегда человеку | нет требований или нет проверок |
| §4.2: проверки объединения | повторяются в копии объединения после разрешения | «Готово» объединения — по его собственным записям |
