# Этап C4: лимит провайдера, уведомления доски, возврат к EXP-SPEC-01

**Статус: ревизия 2, после первого круга ревью (скептик, критик), 2026-10-19.** Уточняет подэтап C4 [этапа C](stage-c-parallel.md):
§2.4, §6.3, §8, §9 и решение владельца 6. Отличия от этапа C собраны в §8.

Ревизия 1 опиралась на неверные допущения:
- она разбирала историю хода, а история хранит только начало хода (§1);
- она считала, что ожидание не тратит минуты бюджета, а оно их тратит (§2.4);
- она восстанавливала ожидание после перезапуска, хотя автопилот при перезапуске выключается (§2.6);
- она пропускала запуск разрешения конфликта C3, который на лимите зависает (§3).

## 0. Что есть сейчас

Факты собраны чтением кода и CLI, без модельных вызовов.

**Пауза.** Ход, упавший на лимите провайдера, ставит запуск на паузу `environment_error`. Этап C §0, §1 (сценарий 5) и
§2.4 предполагали `external_failure`. На деле:
- исход хода `failed` даёт `environment_error` (`pauseForOutcome`, `orchestrationService.ts:2963`);
- `external_failure` бывает только у проверок и подготовки (`cycle.ts:283`).

**Кадры хода.**
- Каждый кадр видит наблюдатель (`turn.ts:342`).
- История кадров хранит только начало хода: первые 1000 событий или 8 МБ, дальше — ничего (`jsonl.ts:199, 224`).
- Отдельно от истории хранится только событие сессии (`jsonl.ts:197`).

**Codex** (app-server):
- уведомление `error` попадает в ленту активности как запись `error` с `params.error.message` (`activity.ts:240`);
- окно распознаёт «hit your usage limit … try again at …» регуляркой (`runModel.ts:486`, `pauseCause`). Время сброса
  не разбирается;
- поля `codexErrorInfo` и `willRetry`, уведомление `account/rateLimits/updated` не читаются;
- единственная записанная реальная строка: «You’ve hit your usage limit. … try again at Sep 28th, 2026 11:51 PM.»
  (codex-cli 0.155.1, `evidence/real-stage-13/series-S3-S5-S6-attempt2`).

**Claude** (stream-json):
- `result` с ошибкой даёт в ленте «CLI reported an error (<subtype>)» без текста (`activity.ts:156`);
- `rate_limit_event` отбрасывается (`activity.ts:160`);
- реальная запись лимита Claude отсутствует.

**Автопилот.**
- На паузе `environment_error` последовательный шаг выключается (`run_paused`, `taskBoard.ts:465`), параллельный даёт
  `halt` (`taskBoard.ts:537`).
- Проверки `take`, `merge` и `agent` стоят раньше `halt` (`taskBoard.ts:566–583`).
- Минуты бюджета считают паузу рабочим временем, если её причины нет в `WAIT_PAUSES` (`activeMs`,
  `taskBoard.ts:423, 438`).
- Автопилот живёт в памяти; перезапуск приложения его выключает (`boardAutopilot.ts:5`). Шаг идёт раз в 1,5 с
  (`boardAutopilot.ts:177`).

**«Продолжить»** — команда `resume` (`orchestrationService.ts:2433`). Её принимают паузы `environment_error` и
`external_failure`. Порядок проверок: сначала ревизия, потом состояние (`orchestrationService.ts:2421, 2435`). Manager
перед ней проверяет тестовую БД (`manager.ts:1295`).

**Запуск разрешения C3.** Слежение разбирает только `completed`, `stopped`, `failed` и `paused limit_reached`
(`manager.ts:979–987`). На любой другой паузе объединение навсегда остаётся «идёт» с `agent.pending` и держит место.

**Что сообщают CLI** (установленные Claude Code 2.1.303 и codex-cli 0.162.0). Строки Claude взяты из исполняемого
файла. Схема Codex снята `codex app-server generate-json-schema`; хеш `~/.codex/config.toml` до и после совпал.

| CLI | Признак лимита | Время сброса |
|---|---|---|
| Claude | кадр с `rate_limit_info.status: "rejected"`: событие `rate_limit_event` или ошибка `usage_limit_reached` с `api_error_params.rate_limit_info` | `rate_limit_info.resetsAt`, секунды эпохи |
| Codex | `codexErrorInfo: "usageLimitExceeded"` в `error` или `turn.error` | окна последнего `account/rateLimits/updated` этого хода (`primary`, `secondary` с `usedPercent ≥ 100`), `resetsAt` в секундах; иначе текст «try again at <Mon> <D><st/nd/rd/th>, <YYYY> <h>:<mm> <AM/PM>» в местном времени |

`rateLimitExceeded` у Codex — временное ограничение частоты: CLI повторяет сам (`willRetry`). Лимитом оно не считается.

## 1. Распознавание

### 1.1. В потоке кадров

`TurnCollector` хранит сигнал лимита отдельно от истории, как событие сессии, и обновляет его на каждом кадре. Длина
хода на сигнал не влияет.

```ts
limit: { provider: "claude" | "codex"; hit: boolean; resetsAt: number | null; source: "rate_limit_info" | "codex_error" | "codex_text";
         windows: number | null /* наибольший resetsAt окон с usedPercent ≥ 100 */; text: string | null } | null
```

- **Claude:** каждый кадр с `rate_limit_info` (событие или ошибка). `status: "rejected"` → `hit: true` и
  `resetsAt = rate_limit_info.resetsAt`. Последний кадр побеждает: `rejected`, а затем `allowed` дают `hit: false`.
  Тип лимита (сессия, неделя, модель) не важен — берётся `resetsAt` кадра, который отказал.
- **Codex:**
  - `account/rateLimits/updated` обновляет `windows`;
  - `codexErrorInfo: "usageLimitExceeded"` даёт `hit: true`. Время — `windows`, иначе разобранный текст сообщения;
  - текст без `codexErrorInfo` (старые CLI) — тоже `hit: true` с источником `codex_text`.
- **Текст Claude** запасным путём не служит: в ленте его нет. Лимит Claude без кадра `rate_limit_info` остаётся
  `environment_error`, без ожидания.

### 1.2. Запись в ленту

Если ход не удался и `limit.hit`, main пишет запись в ленту хода. Запись идёт **раньше** записи `turn_finished`
(`orchestrationService.ts:1249`) и раньше паузы в журнале (`orchestrationService.ts:1279`). Так шаг автопилота
никогда не увидит паузу без признака лимита.

Вид записи — существующий `error`: старые сборки покажут его строкой.

```json
{ "kind": "error", "text": "Claude: usage limit reached · resets 2026-10-19 15:00 UTC",
  "detail": { "limitProvider": "claude", "limitResetsAt": "2026-10-19T15:00:00.000Z", "limitSource": "rate_limit_info" } }
```

- Текст записи — по-английски и с UTC, как остальная лента. Окно показывает своё (§5).
- `limitResetsAt` проверяется **при записи**, относительно конца хода. Время дальше 7 суток — `null`. Время в прошлом
  не дальше 1 часа хранится как есть, раньше — `null`. `limitProvider` и `limitSource` заполнены всегда.
- **Отступление от принципа 8.** Автопилот действует по ленте, а лента пишется «как получится»: после 4 МБ — только в
  память, ошибки записи не видны (`activity.ts:2–4, 23, 405`). Поэтому: записи нет — время сброса неизвестно, и
  автопилот ждёт человека. Сам журнал не меняется.

### 1.3. Одна классификация

`pauseCause` и `pausedTurn` переезжают из `runModel.ts` в `src/shared/orchestrationPause.ts` без изменения поведения.
Это отдельный шаг с тестом на записанных лентах. Затем `pauseCause` читает запись §1.2 первой; регулярка Codex остаётся
для старых запусков.

`RunTaskFacts.providerLimit: { provider, resetsAt: number | null } | null` выводится в main по `pauseCause`. Признак
есть у запуска на паузе `environment_error`, если пауза — лимит.

## 2. Автопилот

### 2.1. Место проверки в шаге

Лимит проверяется **раньше** `run_paused` и `halt` в обоих шагах, а в параллельном — и раньше `take` и `agent`:
- пока у любого запуска проекта (своего, чужого или разрешения C3, §3) есть `providerLimit`, автопилот не берёт новых
  задач и не отдаёт конфликты агенту. Подписка на оба провайдера одна (этап C §2.2): новый запуск упрётся в тот же
  лимит и займёт место;
- `merge` разрешён: в объединении нет ходов модели;
- состояние автопилота: `waits: "provider_limit"` и новое поле `limit: { provider, resetsAt: number | null, key }` —
  самый ранний известный сброс среди запусков на лимите.

### 2.2. Кого продолжает

Сам автопилот продолжает только **свои** запуски: из `started` (задачи) и `agents` (разрешения C3). Запуск, начатый
человеком, — только причина ждать. Его продолжает человек, и автопилот идёт дальше, когда тот снова работает.

### 2.3. Когда продолжает

- **Время известно:** на первом шаге, где `Date.now() ≥ resetsAt + 60 с`, шлётся `resume`. Шаг идёт раз в 1,5 с и
  каждый раз сравнивает часы. Поэтому сон Mac и перевод часов не теряют момент: после пробуждения продолжение уходит
  на первом же шаге. Запас 60 с — на расхождение часов провайдера и Mac.
- **Время уже прошло** к моменту чтения (Mac спал, автопилот включили позже) — продолжить на ближайшем шаге.
- **Время неизвестно:** ждать «Продолжить» человека.

### 2.4. Отказы и счётчик

- Продолжение — через `BoardAutopilotDeps.resume(runId)` → `manager.command(… { kind: "resume" })` с ревизией из
  свежего снимка.
- **Отказ `stale_revision` или `invalid_state`** (человек успел первым, запуск уже идёт или остановлен) — ничего не
  писать, перечитать на следующем шаге. **Другой отказ** (`test_database_unsafe`, `run_not_found`, …) — выключиться с
  кодом `resume_failed` и деталью.
- Поле `resumed: { runId, key, provider, at }` пишется **только после принятого** `resume`.
- **Счётчик:** у запуска не больше 3 автоматических продолжений **подряд**. Счётчик обнуляется, когда у этого
  запуска завершается ход (`turn_finished completed`), то есть лимит был пройден. Если после продолжения лимит снова и
  новое время не позже прежнего, время считается неизвестным. После 3 продолжений подряд — ждать человека; окно
  говорит «Лимит Claude повторился 3 раза — продолжите вручную».
- **Бюджет:** пауза с `providerLimit` не считается рабочим временем. `activeMs` получает признак из фактов и считает её
  ожиданием. Ожидание не тратит ни запусков, ни минут. Если бюджет кончился ещё до сброса, это обычная остановка
  «бюджет», без `resume`.
- **Человек выключил автопилот** во время ожидания: продолжения нет, запуск остаётся на паузе.

### 2.5. Настройки проекта менялись во время ожидания

Продолжение старого запуска — не новый запуск, поэтому правило этапа C §8 «новые не начинаются» его не касается. Запуск
идёт со своей целью из журнала.

### 2.6. Перезапуск приложения

Автопилот выключен, как всегда после перезапуска (`boardAutopilot.ts:5`, этап C §8): само ничего не продолжается.
Запуск остаётся на паузе, окно показывает «Лимит Claude до 15:00» (§5).

Человек нажимает «Продолжить» у запуска или включает автопилот. Новый автопилот не считает старый запуск своим (его
`started` пуст): ждёт, пока человек его продолжит. Счётчик продолжений после перезапуска начинается с нуля.

## 3. Запуск разрешения C3 на паузе

Слежение за разрешениями (`syncResolutions`) разбирает и паузы:

| Пауза запуска разрешения | Объединение |
|---|---|
| `environment_error` с `providerLimit` | остаётся «агент разрешает конфликт», строка «ждёт лимита Claude до 15:00». Свой запуск автопилот продолжает по §2.3. Запуск, начатый «Поручить агенту», продолжает человек («Открыть запуск» → «Продолжить») |
| пауза ожидания человека (`WAIT_PAUSES`: вопрос агента и т. п.) | остаётся, строка «агент ждёт вас», «Открыть запуск» |
| любая другая пауза (`environment_error` без лимита, `protocol_error`, `invalid_report`, …) | `merge_agent_failed` с деталью `paused:<reason>` |

Пока у разрешения лимит, шаг `agent` не выдаётся (§2.1).

## 4. Уведомления (этап C §6.3)

Уведомления добавляются в `notify.ts`. Хук уведомлений получает итог доски (`BoardView.heads`) и состояние
автопилота.
- **«Объединение T-2 — конфликт, решите»:**
  - когда: пауза объединения `merge_conflict`, `merge_checks_failed`, `merge_agent_failed`, `merge_budget`;
  - не уведомляют: `merge_waits_slot`, идущее разрешение, `merge_wait`;
  - ключ — `merge:<runId объединения>:<причина>`. Он хранится в той же записи `orch.notified.v1` (localStorage),
    поэтому перезапуск не повторяет уведомление;
  - объединение, впервые увиденное без записи, только записывается — как запуски;
  - клик открывает доску и прокручивает к строке итога доски, а не запуск.
- **«Лимит сброшен, продолжаю: T-2»:** по `resumed` автопилота, ключ `resumed:<linkId>:<at>`. Клик открывает запуск.
- **«Итог доски обновлён: T-1, T-2 · проверки прошли»:**
  - выключено по умолчанию;
  - одно на смену вершины, ключ `head:<ref>:<commit>`. В тексте задачи, влитые с прошлого уведомлённого коммита;
  - несколько объединений подряд, пока окно в фокусе, не уведомляют.
- **Настройка `boardHead: false`:**
  - добавляется в `NotificationSettings`, `DEFAULT_NOTIFICATIONS` и `normalizeNotifications` (`settingsStore.ts:495,
    500`) и в `DEFAULT_NOTIFY_PREFS` (`notify.ts:13`);
  - переключатель — под «Доска», недоступен, когда «Доска» выключена;
  - старая сборка при записи настроек это поле сотрёт: безвредно, по умолчанию оно выключено.
- **Значок Dock** прибавляет объединения, ждущие человека. Запуски на лимите уже считаются: `environment_error` — пауза
  «ждёт вас».
- Все уведомления доски подчиняются настройке «Доска» (`prefs.board`).

- завтра — `завтра 15:00` / `tomorrow 3:00 PM`;
- позже — `24 окт. 15:00` / `Oct 24, 3:00 PM`;
- местное время Mac.

## 6. Возврат к EXP-SPEC-01

**Где:** раздел «§11. Проверка готовности (<дата>)» в EXP-SPEC-01, а также:
- строка в журнале статуса §10;
- статус в шапке;
- строка C4 в ROADMAP и в этапе C §9.

**Форма:** по каждому пункту §9 — «готово», «нет» или «частично», с доказательством (документ, путь в коде, PR) и тем,
чего не хватает.

**Ожидаемые ответы:**
1. **A–C приняты внешним ревью** — нет: внешнее ревью не проведено (ROADMAP, «Перед публикацией»). Нужно: ревью.
2. **Зависимости B и параллельные копии C с проверкой объединения** — готово (B, C1–C3).
3. **Способ записать предположение и версии** — частично: есть база запуска (`goal.base`, вершина доски). Нет версии
   контракта зависимости, условия подтверждения и отмены, состояний «предварительный / устаревший» (EXP §3). Нужно:
   модель данных D.
4. **Критерии принятия и набор сопоставимых задач** — предлагаются в разделе, до прогонов (EXP §6): 3–4 пары задач
   «A → B» на фикстурном проекте, метрики §6, порог «время до проверенного итога меньше на ≥ 20 % при той же
   успешности, без внешних эффектов».
5. **План пилота** — предлагается: объём, бюджет вызовов, число прогонов (чередование), сценарии §7.

**Итог:** «к пилоту не готово, нужно: внешнее ревью A–C и модель данных D». Это допустимый результат: возврат к
эксперименту обязателен, готовность — нет. Решение о пилоте и о внешнем ревью принимает владелец. Прогонов нет.

## 8. Совместимость и проба

- **Журнал** не меняется.
- **Лента** — существующий вид `error`: старые сборки показывают строку.
- **Настройки:** `boardHead` старые сборки стирают при записи настроек; по умолчанию оно выключено.
- **Реальная проба** не планируется: лимит нельзя вызвать по желанию. Распознавание Claude опирается на формат из CLI,
  а не на запись реального случая. В ROADMAP — открытое ограничение: «при первом реальном лимите любой CLI сохранить
  ленту хода и сырые кадры в evidence; закрывается этой записью».
