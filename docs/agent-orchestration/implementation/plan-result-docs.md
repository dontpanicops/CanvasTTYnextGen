# Документы «План» и «Результат» запуска

Статус: реализовано, на ревью (2026-10-14). Спецификация приведена к тому, что построено; расхождения с черновиком — ниже по тексту. Черновик ждал утверждения владельца (2026-10-11). Первая из четырёх частей, о которых договорились
2026-10-11:

1. документы «План» и «Результат» (этот файл);
2. правка плана человеком;
3. скептик плана;
4. «ломатель».

Ревизия 2 — после проверки скептиком: 13 находок, 3 блокирующих. Все учтены, см. §9.

## 1. Зачем

Владелец: «нужно, чтобы они выводили план и результат отдельно, чтобы легко было прочитать, понять, изменить».

Сейчас:

- План виден только названиями этапов. Задание этапа и условия готовности видны в «Итоге» по отдельности, а целиком —
  только на паузе проверки плана (`RunPanel.tsx`, `orch-summary__plan`).
- «Итог» (`RunSummary`) — подробный отчёт о ходе запуска: источник каждого факта, раунды, ревью, проверки. Прочитать
  его как короткий документ «что сделано» трудно.
- Если результат задачи — документ (пример: задача, которая пишет разбор кода в
  `docs/…/review.md`), его можно прочитать только как diff во вкладке «Изменения».

Успех: человек открывает запуск и за минуту читает два документа:

- **План** — что агенты собираются сделать и как поймут, что сделали.
- **Результат** — что сделано, выполнены ли требования, что осталось и как забрать. Документ, который создала задача,
  читается здесь же как текст.

Каждый документ можно скопировать или положить на холст заметкой, чтобы перечитать, дописать свои пометки или вставить
в задачу. Подробности хода запуска остаются в «Итоге».

## 2. Что не меняется

- **Источник правды** — журнал запуска и состояние в main (принцип 8, AUTOMATIC-TASK-CYCLE). Документы *выводятся* из
  них, отдельно не хранятся, в журнал ничего нового не пишется. Формат журнала не меняется.
- **Агентам ничего нового не поручается**: ни план, ни результат в файлах они не пишут. Документ, написанный агентом, —
  не доказательство (принцип 2). Документ собирает приложение из того, что уже записано.
- **«Итог» остаётся** подробным отчётом с источниками фактов: этапы и раунды, ревью, проверки по командам, все
  замечания, «что дальше». «Результат» эти списки не повторяет (§3.2).
- **Права, цикл, журнал** не меняются. В main и IPC добавлены чтение `orchestration:file` (точный
  текст файла из дерева запуска; ничего не пишет; `readTreeFile`, `manager.file`) и поле `source` у заметки в
  `SettingsStore`. Остальное renderer уже получает: `view.progress`, история журнала,
  тексты через `loadText`, изменения через `api().changes` и `api().diff`.

## 3. Документы

Один генератор на документ — чистая функция в новом `src/renderer/src/features/orchestration/runDocs.ts`:

```ts
interface DocSection { heading: string; collapsed?: boolean; lines: DocLine[] }
type DocLine = { kind: "text"; text: string; said?: string } // said: чьё слово («со слов исполнителя»), уже на языке человека
  | { kind: "item"; text: string; mark?: "met" | "not_met" | "not_checked" | "dropped" | "open" }
  | { kind: "file"; path: string; body: string | null; note: string | null }; // note: почему текста нет или как он прочитан
interface RunDoc { title: string; asOf: string; sections: DocSection[] }

planDoc(input, locale): RunDoc
resultDoc(input, docs: CreatedDocs, locale): RunDoc
toMarkdown(doc: RunDoc): string
addedText(diff: OrchestrationDiff): { body: string | null; why: "too_large" | "binary" | null }
readCreatedFile(path, exact, diff): Promise<CreatedFile> // точное чтение, запасной путь через diff
pickDocs(files): { paths: string[]; more: number }       // добавленные .md/.markdown/.txt, не больше MAX_DOCS
noteText(markdown, cut): string                           // обрезка до NOTE_MAX, суррогатные пары целы
snapshotText(markdown, locale, at): string                // первая строка «> Копия документа на …» и документ
```

`input` — то, что уже есть у `RunSummary`:

- `view` и `records`;
- прочитанные тексты: цель, планы, отчёты;
- `summaryModel(view, records, …)`;
- список изменений и прочитанные diff созданных документов.

Если текст ещё не прочитан, документ пишет «загружается». Если прочитать не удалось — так и говорит. Выдумывать на
месте недостающего нельзя (как `NotSpecified` в «Итоге»).

React-компонент `RunDocView` рисует `RunDoc`: заголовки, абзацы, списки с отметками, свёрнутые разделы через
`<details>`. `toMarkdown` даёт тот же документ текстом для копирования и заметки. Обе формы строятся из одного `RunDoc`,
поэтому разойтись не могут. Пометка «со слов исполнителя» (`said`) попадает и в markdown.

### 3.1 «План»

Заголовок — `T-1 · <название задачи> — план`. Если запуск не с доски — по первой строке цели.

1. **Цель** — текст цели как задал человек.
2. **Требования** — R1…Rn с текстом. Требование, которое человек снял, помечено «снято» с причиной.
3. **Этапы** — для каждого этапа плана в силе:
   - номер и название;
   - задание этапа полностью;
   - условия готовности: C*n* с текстом, чем подтверждается («проверка `npm test`», «изменение в файлах», «ваше
     решение») и какие требования закрывает;
   - состояние этапа одним словом из `summaryModel`: ждёт, идёт, принят, на исправлении.
4. **Перепланирования** — свёрнуто. Если план менялся: версия, с какого этапа, что снято и почему.
5. **Вопрос лида** — если в плане есть `question`.

Источник: тексты `plan.recorded` (`PlanText`, `conditions.ts`), `progress.conditions`, `summaryModel`.

Журнал v1 (`progress.conditions == null`): разделы «Требования» и условия этапов пропускаются, этапы — по `parsePlan`.

### 3.2 «Результат»

Заголовок — `T-1 · … — результат`, строка «по состоянию на <время>».

1. **Итог одной строкой** — та же функция, что в «Итоге» (`outcomeKey` и тексты `orchSumOutcome_*`): «Готово —
   подтверждено проверками», «Готово, но проверок нет», «Остановлено: …», «Идёт». Под ней одной строкой: «Проверки:
   *k* из *n* прошли», «Открытых блокирующих замечаний: *m*». Подробности — ссылкой на «Итог».
2. **Что сделано** — по принятым этапам: название и `summary` отчёта исполнителя (`reportParts`), с пометкой «со слов
   исполнителя».
3. **Требования** — R*n* с отметкой: выполнено, не выполнено, не проверено, снято. Отметки — из
   `progress.conditions.requirements`. В журнале v1 раздела нет.
4. **Созданные документы** — текст новых документов задачи (§3.3).
5. **Как забрать** — одна строка:
   - «результат в отдельной копии, ваша папка не менялась — кнопка „Забрать результат“»;
   - или «результат уже в ветке `<имя>` / в рабочей папке» (`take`);
   - или «запуск работал в рабочей папке, изменения уже там».

Список изменённых файлов, проверки по командам, все замечания и «что дальше» в «Результат» не входят: они в «Итоге» и
«Изменениях».

### 3.3 Созданные документы

Берутся *добавленные* файлы (`status: "added"` в `api().changes`) с расширением `.md`, `.markdown` или `.txt`. Не больше
10 файлов, по порядку списка. Остальные идут строкой «ещё *k* документов — во вкладке „Изменения“».

Текст файла читается **точно**: `api().file(runId, path)` (`orchestration:file`) отдаёт блоб `git cat-file blob
<дерево>:<путь>` из `control.git` запуска. Дерево то же, что у вкладки «Изменения» (живой снимок, последняя проверка или
последняя контрольная точка), поэтому текст совпадает со списком файлов; лимит 256 КиБ. Чтение работает и после
удаления рабочей папки или worktree, пока жив `control.git` запуска.

**Запасной путь** — только когда точное чтение не удалось: текст восстанавливается из `api().diff(runId, path)`, и у файла
стоит пометка «Восстановлено из изменений…» (в панели и в markdown), чтобы он не выглядел точным. Если точное чтение
сказало «больше 256 КиБ» или «не текст», diff не запрашивается. Если у запуска нет `control.git`, не работает ни то, ни
другое: «не удалось прочитать» (обе дороги идут через него).

Восстановление из diff — чистая функция `addedText`. Это unified diff `-U3` от `diffTreePath` (`workspace.ts`), лимит
256 КиБ:

- всё до первой строки `@@` пропускается (`diff --git`, `new file mode`, `index`, `---`, `+++`);
- строки `@@ …` пропускаются;
- у строк с `+` снимается ровно один `+`;
- строки `\ No newline at end of file` пропускаются;
- `Binary files … differ` → `why: "binary"`, текста нет;
- `truncated: true` (main отдаёт пустой текст) → `why: "too_large"`: «документ больше 256 КиБ — откройте во вкладке
  „Изменения“». Начала файла в этом случае нет, и документ его не обещает;
- CRLF сохраняется как есть.

Когда текста нет:

- **Ошибка `api().changes` или `api().diff`** (копии больше нет, `run_not_found`, другой отказ main). Раздел пишет «не
  удалось прочитать: <причина>» и даёт кнопку «Повторить», как вкладка «Изменения».
- **Запуск более новой версии** (`view.newer`). Раздел пропускается без вызова `api()`: для таких запусков main
  изменения не отдаёт, вкладки «Изменения» тоже нет.
- **Какое дерево показано.** Под разделом, когда есть документы, всегда строка из `orchChangesAt_<at>` — как во вкладке
  «Изменения», а не только для «не финального» дерева.

Чтение: `api().changes` — при смене `seq`, с задержкой 300 мс, как во вкладке «Изменения». Файл перечитывается только
если изменился ключ дерева. Вызовы идут по одному, не параллельно.

Кэш созданных документов: ключ дерева — `${at}:${atTs ?? s<seq>}` плюс путь (не `atTs:path`: при `atTs = null` ключ был
бы неоднозначен). Кэш другого дерева удаляется. Восстановленный (из diff) и недоступный текст не кэшируется — он
перечитывается при следующем обращении, точный остаётся.

Пометки: «со слов исполнителя» стоит только у прочитанного отчёта. Этапы, задания и условия — текст лида; это сказано один
раз строкой «Этапы, задания и условия — со слов лида.». Заголовок этапа при непрочитанном плане — «загружается…» (или
«не удалось прочитать»), а не «не указано». Worktree без ветки в «Как забрать» даёт строку про копию, а не «`?`».

## 4. Где видно

1. **Панель запуска.** Две новые вкладки, первыми: **«План»** (`plan`) и **«Результат»** (`result`), затем прежние
   «Итог», «Обзор», «Действия», «Изменения», «Лог», «История». Что меняется в коде:
   - `PanelTab` и список вкладок (`RunPanel.tsx`, `tabs`; для `view.newer` — тоже обе);
   - строки `orchTab_plan` и `orchTab_result` (русский и английский);
   - широкая панель (`orch-panel--wide`) — для `summary`, `plan` и `result`;
   - `setEndedHere(false)` — при открытии `summary` или `result`.
2. **Вкладка по умолчанию** не меняется (`useAgentCanvasUi.ts`, `summary`). Меняется только «Итог готов — открыть»
   (`orchSummaryOpen`) по окончании запуска: кнопка ведёт на «Результат».
3. **Пауза проверки плана** (`awaiting_plan_review`). Список этапов в шапке (`orch-summary__plan`) заменяется ссылкой
   «Открыть план», которая ведёт на вкладку «План». Кнопки «Утвердить» и «Вернуть с заметками» остаются в шапке, где они
   сейчас. Второго рендера плана нет.
4. **Кнопки документа** — над каждым документом:
   - **«Копировать»** — `toMarkdown` в буфер обмена;
   - **«На холст»** — заметка с этим текстом (§5).
5. **Карточка задачи на доске** — кнопки «План» и «Результат» есть, когда у задачи есть запуск (`st.current`,
   `BoardCard.tsx`). Открывают панель через `ui.openRunById(runId, tab)`. У задачи без текущего запуска кнопок нет:
   её прошлые запуски открываются из истории пространства, как сейчас.

## 5. Заметка на холсте

Заметки остаются как есть: простой текст в `settings.json`, без markdown.

Цепочка вызова: `WorkspaceCanvas` уже создаёт заметки (`createNote` → `onCreateStickyNote` → `App.createStickyNote`).
Новый колбэк `onNoteFromText(markdown, {runId, doc})` идёт `WorkspaceCanvas` → `OrchestrationOverlays` →
`OrchestrationDialogs` → `RunPanel` (`AgentScene` в цепочке нет). В `WorkspaceCanvas` он делает то же, что `createNote`:

- точка — центр видимой части холста слева от открытой панели запуска (под панелью заметку не видно); отклик на кнопке —
  «На холсте ✓»;
- заметка — `stickyNoteAtPoint`, потом `{ …note, text }`;
- размер не меняется (по умолчанию для заметки, пользователь растянет сам).

Заметка попадает в **активное пространство**: `createStickyNote` берёт `activeIdRef.current`. Панель запуска открыта
на холсте этого пространства, так что это пространство, которое человек видит. Отдельного размещения у карточки
исполнителя нет.

Текст заметки:

- первая строка — «> Копия документа на <дата, время>», затем сам документ;
- не больше 20 000 символов **вместе** с этой строкой и хвостом (столько хранит `SettingsStore` и пропускает `maxLength`
  поля заметки; черновик говорил 30 000). Всё, что длиннее, отрезается, в конце строка «… обрезано — документ целиком во
  вкладке запуска.» (`docNoteCut`); суррогатные пары не рвутся. Это нужно потому, что заметки хранятся в `settings.json`, а он
  пишется целиком при каждой правке.

У заметки-снимка необязательное поле `source` — `{ runId (UUID), doc: "plan" | "result", at (ISO) }`. По нему на заметке
рисуется плашка «Копия на <время>» (en: «Copy as of <time>»; переносится, время видно целиком) и кнопка «Открыть актуальный», которая открывает текущую вкладку запуска. После
перепланирования снимок остаётся помеченной копией и не выдаёт себя за текущий план. Заметка без `source` (старая
версия) — обычная; старые версии приложения поле отбрасывают, текст остаётся.

Это **снимок**, а не живая связь. Заметку можно править, дописывать, удалять — на запуск это не влияет. Повторное «На
холст» создаёт новый снимок.

Живую заметку, связанную с запуском, и markdown в заметках не делаем. Иначе у плана появятся два источника правды. Если
снимков окажется мало, вернёмся к этому отдельно.

## 6. Не входит

- Правка плана — часть 2. Сейчас «изменить» — это «Вернуть с заметками» на паузе плана и правка своей копии-заметки.
- Запись `plan.md` и `result.md` в проект при «Забрать результат». Это меняет дерево проекта, нужно отдельное решение
  владельца.
- Изменение лимита 256 КиБ. Документы больше читаются во вкладке «Изменения».

## 7. Проверка

**Модульные тесты** — `tests/orchestration-run-docs.test.mjs`, на чистых функциях. Импорт `runDocs.ts` напрямую, как
`orchestration-board-ui.test.mjs` импортирует `boardModel.ts`. Входы собираются в тесте вручную, как в
`orchestration-conditions.test.mjs`: записи журнала v2 и `view`.

1. План из двух этапов с условиями: в документе все C*n*, их подтверждение и R*n*.
2. Перепланирование со снятым условием: раздел свёрнут, причина видна.
3. Непрочитанный текст плана: «загружается», ничего не выдумано.
4. Журнал v1 (`conditions: null`): этапы есть, разделов требований нет.
5. `addedText`:
   - новый файл;
   - файл без перевода строки в конце;
   - CRLF;
   - строка файла, которая сама начинается с `+` или `@@`;
   - бинарный;
   - `truncated`.
6. «Результат», когда «готово, но проверок нет»: строка итога совпадает с текстом «Итога».
7. «Созданные документы»:
   - 12 добавленных `.md`: показаны 10 и строка «ещё 2»;
   - `.ts` не берётся;
   - нет точного чтения и нет diff → «не удалось прочитать»;
   - `view.newer` → раздела нет.
8. `toMarkdown`:
   - заголовки `#` и `##`, списки `-`, отметки ✓ ✗ … —;
   - «со слов исполнителя» на месте;
   - без HTML;
   - обрезка заметки до 20 000 символов (вместе с плашкой и строкой в конце), без разрыва суррогатной пары.
9. `readCreatedFile`:
   - точный текст есть — diff не запрашивается;
   - «больше лимита» или «не текст» от точного чтения — окончательно, diff не запрашивается;
   - точное чтение не удалось — текст из diff с пометкой «восстановлено»;
   - не удалось ни то, ни другое — «недоступно»;
   - diff без нового файла или без блока изменений — не пустой документ; новый пустой файл — пустой документ.
10. `snapshotText` и `noteText`: первая строка говорит, что это копия и на когда, документ следует без изменений; строка
    копии переживает обрезку, вся заметка укладывается в `NOTE_MAX`; обрезка на суррогатной паре снимает всю пару.
11. Main (`tests/orchestration-native.test.mjs`): `manager.file` отдаёт точный текст добавленного файла и отказывает
    (`invalid_argument`) для пути, которого нет в изменениях запуска; `readTreeFile` — точные байты блоба, большой не
    читается, пути вне дерева отклоняются.
12. Настройки (`tests/canvas-launcher-settings.test.mjs`): нормализация `source` у заметки — заметка хранит, откуда
    снимок; неверный `source` отбрасывается, заметка остаётся.
